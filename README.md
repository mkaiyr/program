# Кафе Бистро — кассовая система

Настольное приложение для небольшого кафе: касса, экраны кухни и бара, управление меню.
Интерфейс — Python 3.12 + Tkinter/ttk, данные и права доступа — Supabase (PostgreSQL, Auth, RLS).

## Возможности

| Роль | Что доступно |
|---|---|
| **Кассир** (`cashier`) | Каталог блюд с поиском по коду и названию, корзина, оформление заказа, свои заказы, выдача готового заказа |
| **Администратор** (`admin`) | Всё, что у кассира, для всех заказов; управление меню (коды, цены, категории, станция, доступность); явная принудительная готовность заказа |
| **Кухня** (`kitchen`) | Кухонные позиции активных заказов без цен, «Начать готовить» / «Готово» для своей части заказа, отметка наличия блюд |
| **Бар** (`bar`) | Барные позиции активных заказов без цен, «Начать готовить» / «Готово» для своей части заказа |

Основное:

- вход по коду сотрудника и паролю (пароль проверяет Supabase Auth);
- постоянный числовой код у каждой позиции меню (1001, 1002, …) и поиск по коду или названию во всех панелях;
- раздельное приготовление на кухне и в баре: заказ «Готов», только когда готовы все станции;
- автообновление экранов кухни и бара каждые 7 секунд, звуковой сигнал только о новых заказах;
- все изменения данных — через серверные функции с проверкой роли; у клиента только чтение под RLS.

## Структура

```
main.py              точка входа, выбор экрана по роли
config.py            чтение config.ini (запрещает секретные ключи)
db.py                работа с Supabase: вход, меню, заказы, станции
search.py            общий поиск по коду и названию
ui_theme.py          общий стиль интерфейса и виджеты
ui_login.py          экран входа
ui_order.py          касса
ui_orders.py         окно «Заказы» (кассир, администратор)
ui_admin.py          управление меню
ui_kitchen.py        экраны кухни и бара (заказы, автообновление, звук)
ui_kitchen_menu.py   вкладка «Меню» кухни (наличие блюд)
sql/01…08_*.sql      миграции базы — применяются вручную по порядку
sql/seed/            тестовое меню для нового проекта (не миграция)
sql/tests/*.sql      SQL-проверки прав и логики (выполняются в транзакции и откатываются)
tests/               локальные тесты (unittest, без подключения к Supabase)
docs/                архитектура, база данных, разработка, отчёт об изменениях
```

## Установка и запуск

```bash
python3.12 -m venv .venv
source .venv/bin/activate            # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp config.example.ini config.ini     # затем вписать URL проекта и публичный ключ
python3.12 main.py
```

В `config.ini` указывается **только публичный ключ** (`sb_publishable_…` или `anon`). Секретный ключ
и `service_role` приложение не принимает. `config.ini` не попадает в Git (`.gitignore`).

База данных настраивается миграциями из `sql/` — порядок и проверки описаны в [docs/DATABASE.md](docs/DATABASE.md).
**Версия приложения в этом репозитории требует миграций 07 и 08** (колонки `code` и `station`).

Первая установка базы (подробно — [docs/DATABASE.md](docs/DATABASE.md#первая-установка-новый-проект-supabase)):

1. `sql/01_schema.sql` … `sql/08_bar_stations.sql` по порядку, каждый целиком, один раз.
2. Пользователи и профили (admin, cashier; при необходимости kitchen, bar) — команды в конце файлов миграций.
3. Меню: на тестовом проекте — `sql/seed/demo_menu.sql`; на рабочем — через «Управление меню» в приложении.
4. Напитки — на станцию `bar` (ручной шаг из конца 08).

> **⚠️ Миграции применяются строго по порядку 01 → 08, каждая один раз.** На базе, где уже есть
> 07/08, файлы 01, 02, 04, 05, 06 повторно не запускать: они вернули бы старые правила заказов и
> меню, а 05 удалила бы роль `bar`. Текущие версии этих файлов останавливаются до изменений
> (`ОСТАНОВЛЕНО: …`), но их версии в истории Git (коммит `e819f75` и раньше) такой защиты не имеют. Сначала
> тестовый проект Supabase, на рабочей базе — только после резервной копии. Подробности и
> восстановление — [docs/DATABASE.md](docs/DATABASE.md#повторный-запуск).

## Тестирование

```bash
python3.12 -m py_compile *.py tests/*.py
python3.12 -m unittest discover -s tests -v
```

Локальные тесты работают на заглушках и не подключаются к Supabase. Права и логику базы
проверяют SQL-скрипты `sql/tests/*_checks.sql` — см. [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md).

## Основные сценарии

1. **Продажа.** Кассир вводит код блюда (Enter добавляет в корзину) или нажимает плитку, оформляет заказ.
   Сервер сам проверяет доступность и цены и считает сумму.
2. **Приготовление.** Заказ появляется на экране кухни и/или бара (только их позиции) со звуковым сигналом.
   Каждая станция отмечает «Начать готовить» → «Готово» для своей части.
3. **Выдача.** Когда готовы все станции, заказ становится «Готов» — кассир отмечает «Выдан».
4. **Меню.** Администратор добавляет позиции (код назначается автоматически или вручную),
   меняет цены, категории и станцию; повар отмечает «Нет в наличии».
