# Кафе Бистро — кассовая система

Настольное приложение для небольшого кафе: касса, экраны кухни и бара, управление меню.
Интерфейс — Python 3.12 + Tkinter/ttk, данные и права доступа — Supabase (PostgreSQL, Auth, RLS).

## Возможности

| Роль | Что доступно |
|---|---|
| **Кассир** (`cashier`) | Каталог блюд (категории, поиск по коду и названию), корзина с подытогом, надбавкой 10% и итогом, оформление заказа, кассовая смена (открытие, внесение и изъятие наличных, закрытие с разницей), свои заказы с поиском и фильтрами, аннулирование своего заказа с причиной, выдача готового заказа |
| **Администратор** (`admin`) | Панель с боковым меню: главная (выручка, заказы, средний чек, сотрудники, смена, последние заказы), касса, управление меню (коды, цены, станция, подтверждение и отклонение позиций кухни и бара), категории, **сотрудники** (создание, роль, код, пароль, активность), кассовые смены, история заказов (аннулирование любого заказа, принудительная готовность, «Удалённые заказы»), **статистика и отчёты** (период, диаграммы, экспорт CSV), настройки с проверкой миграций |
| **Кухня** (`kitchen`) | Кухонные позиции активных заказов без цен, «Начать готовить» / «Готово» для своей части заказа; меню кухни: наличие блюд и предложение новых позиций |
| **Бар** (`bar`) | Барные позиции активных заказов без цен, «Начать готовить» / «Готово» для своей части заказа; меню бара: наличие и предложение новых позиций |

Основное:

- автоматическая надбавка 10% к каждому заказу: подытог, надбавка и итог считаются на сервере (`place_order`), хранятся в заказе и входят в отчёты; кухне и бару она не показывается;
- вход по коду сотрудника и паролю (пароль проверяет Supabase Auth);
- постоянный числовой код у каждой позиции меню (1001, 1002, …) и поиск по коду или названию во всех панелях;
- раздельное приготовление на кухне и в баре: заказ «Готов», только когда готовы все станции;
- автообновление экранов кухни и бара каждые 7 секунд, звуковой сигнал только о новых заказах;
- новые позиции от кухни и бара появляются в продаже только после решения администратора (миграция 09);
- все изменения данных — через серверные функции с проверкой роли; у клиента только чтение под RLS.

```
ui_admin_panels.py   главная, меню, категории, настройки

ui_orders.py         окно «Заказы» (кассир, администратор), кнопка «Удалить»

ui_kitchen.py        экраны кухни и бара (заказы, автообновление, звук)

tests/               локальные тесты (unittest, без подключения к Supabase)
docs/                архитектура, база данных, разработка, отчёт об изменениях
```

## Установка и запуск

```bash
python3.12 -m venv .venv
source .venv/bin/activate            # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp config.example.ini config.ini     # затем вписать URL проекта и публичный ключ
python3.12 main.py
```

Нужен Python 3.12 с Tkinter. Установщик с python.org включает Tkinter; в Python из Homebrew его
может не быть (`ModuleNotFoundError: No module named '_tkinter'`) — тогда `brew install python-tk@3.12`
или Python с python.org.

В `config.ini` указывается **только публичный ключ** (`sb_publishable_…` или `anon`). Секретный ключ
и `service_role` приложение не принимает. `config.ini` не попадает в Git (`.gitignore`).

База данных настраивается миграциями из `sql/` — порядок и проверки описаны в [docs/DATABASE.md](docs/DATABASE.md).
**Версия приложения в этом репозитории требует миграций 07 и 08** (колонки `code` и `station`).
Миграции 11–14 включают новые возможности: 11 — надбавка 10% и аннулирование (**без неё заказы не оформляются**: приложение требует `place_order`), 12 — кассовые смены, 13 — сотрудники, 14 — отчёты и категории; без 12–14 соответствующие разделы сообщают, что функция не настроена на сервере. Раздел «Настройки» администратора показывает, какие миграции применены.
Миграция 09 включает меню станций и решения администратора; без неё приложение работает как раньше
(у бара во вкладке «Меню» — сообщение, что меню появится после обновления базы). Миграция 10 —
удаление заказов; без неё кнопки удаления сообщают, что функция не настроена на сервере.

Первая установка базы (подробно — [docs/DATABASE.md](docs/DATABASE.md#первая-установка-новый-проект-supabase)):

1. `sql/01_schema.sql` … `sql/08_bar_stations.sql`, затем `sql/09_station_menu.sql` … `sql/14_reports_categories.sql` —
   по порядку, каждый целиком, один раз.
2. Пользователи и профили (admin, cashier; при необходимости kitchen, bar) — команды в конце файлов миграций.
3. Меню: на тестовом проекте — `sql/seed/demo_menu.sql`; на рабочем — через «Управление меню» в приложении.
4. Напитки — на станцию `bar` (ручной шаг из конца 08).

> **⚠️ Миграции применяются строго по порядку 01 → 14, каждая один раз** (повторно допустимы только 03 и 09–14; 08 — после неё сразу снова 09 и 11). На базе, где уже есть
> 07/08, файлы 01, 02, 04, 05, 06 повторно не запускать: они вернули бы старые правила заказов и
> меню, а 05 удалила бы роль `bar`. Текущие версии этих файлов останавливаются до изменений
> (`ОСТАНОВЛЕНО: …`), но их версии в истории Git (коммит `e819f75` и раньше) такой защиты не имеют. Сначала
> тестовый проект Supabase, на рабочей базе — только после резервной копии. Подробности и
> восстановление — [docs/DATABASE.md](docs/DATABASE.md#повторный-запуск).

## Тестирование

```bash
python3.12 -m py_compile *.py tests/*.py
python3.12 -m unittest discover -s tests -v
```

Локальные тесты (317) работают на заглушках и не подключаются к Supabase. Права и логику базы
проверяют SQL-скрипты `sql/tests/*_checks.sql` — см. [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md).
Миграции 01–10 и эти проверки пройдены на локальном PostgreSQL 16.2, а 11–14 с проверками 11–14 — на
локальном PostgreSQL 17 (оба с эмуляцией Supabase); на Supabase — ещё нет
([docs/MIGRATION_TEST_PLAN.md](docs/MIGRATION_TEST_PLAN.md), раздел 15).

## Основные сценарии

1. **Продажа.** Кассир вводит код блюда (Enter добавляет в корзину) или нажимает плитку, оформляет заказ.
   В корзине отдельными строками — подытог, надбавка 10% и крупный итог (бургер 3000 + кола 1000 = 4000 + 400 = 4400 ₸).
   Сервер сам проверяет доступность и цены, считает надбавку и сверяет итог с показанным.
2. **Приготовление.** Заказ появляется на экране кухни и/или бара (только их позиции) со звуковым сигналом.
   Каждая станция отмечает «Начать готовить» → «Готово» для своей части.
3. **Выдача.** Когда готовы все станции, заказ становится «Готов» — кассир отмечает «Выдан».
4. **Меню.** Администратор добавляет позиции (код назначается автоматически или вручную),
   меняет цены, категории и станцию. Повар и бармен отмечают «Нет в наличии» и предлагают новые
   позиции своей станции — в продажу они попадают после «Подтвердить» у администратора.
5. **Смена.** Кассир открывает смену с начальной суммой, вносит и изымает наличные, в конце вводит фактическую
   сумму — приложение показывает ожидаемую и разницу (начало + выручка + внесения − изъятия).
6. **Аннулирование.** Ошибочный заказ аннулируется с обязательной причиной: он остаётся в истории с составом и
   суммой, но не входит в выручку и пропадает с экранов кухни и бара.
7. **Удаление заказа.** Выданный заказ кассир (свой) или администратор отправляет кнопкой «Удалить»
   в «Удалённые заказы» — из истории он пропадает, но остаётся в базе. Администратор восстанавливает
   его или удаляет навсегда (предупреждение и ввод номера заказа); в журнале остаются номер, сумма,
   кассир, кто и когда удалил.
