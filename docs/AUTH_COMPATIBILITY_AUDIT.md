# Аудит совместимости миграции 13 (сотрудники) с Supabase Auth

> **Статус: BLOCKED для проверки настоящего Supabase Cloud.** Реальный GoTrue **не проверялся**: у среды нет доступа к Supabase, исходников сервера GoTrue, его миграций, Supabase CLI и Docker.
> Всё ниже проверено на **локальной эмуляции**, которая не является GoTrue. Ничего из описания настоящей схемы Auth здесь не подтверждено официальным источником: оно восстановлено по памяти и везде помечено.
> Production не затрагивался. Дата: 2026-11-16.

## 1. Как устроена авторизация в приложении

```
Экран входа: код сотрудника (4–6 цифр) + пароль
  │  db.sign_in
  ├─ RPC employee_login_email(код)            — anon, SECURITY DEFINER: код → служебный email (<uuid>@bistro.local) активного сотрудника, иначе NULL
  ├─ auth.sign_in_with_password(email, пароль) — проверяет Supabase Auth (GoTrue): пароль, подтверждение email, блокировку
  └─ SELECT profiles (RLS): роль и is_active; код переназначен или сотрудник отключён → выход и отказ
Данные: каждая функция и политика RLS проверяет auth.uid() и is_active_* по таблице profiles (не по токену).
```
Второй системы входа нет. Миграция 13 лишь автоматизирует то, что раньше администратор делал вручную: пара `auth.users` + `auth.identities` + `profiles`.
Деактивация сотрудника — только `profiles.is_active = false`; сессии и токены в Auth не отзываются, доступ к данным закрывают функции и RLS.

| Объект | Что делает | Требования Supabase Auth (по памяти, не подтверждено) | Проверено локально | Неизвестно без настоящего Supabase |

Строковые токен-колонки GoTrue читает в строки Go — NULL ломает вход | Вставка проходит на минимальной и на усиленной эмуляции; токены `''`; вход (по модели) работает | Какие NOT NULL-колонки без значения по умолчанию есть в **вашей** версии схемы; значения по умолчанию других токен-колонок |

| `admin_set_staff_password` | `update auth.users set encrypted_password` | Токены обновления и сессии при смене пароля не отзываются | Старый пароль перестаёт работать, новый работает, остальные записи не затронуты | Поведение действующих сессий после смены пароля |
| `admin_update_staff` | Меняет `profiles` (имя, роль, код, `is_active`) | Auth не знает об отключении | Отключённый не находится по коду; токен, полученный напрямую, данные не открывает | — |
| `employee_login_email` (03/08) | Код → email для `anon` | — | Неверный, пустой, слишком длинный код и «инъекция» не находят учётную запись | — |
| email `<uuid>@bistro.local` | Служебный адрес | Домен `.local` зарезервирован; валидация email зависит от версии GoTrue | Заглушка принимает | Принимает ли ваш GoTrue такой адрес при **входе по паролю** (косвенно: [DATABASE.md](DATABASE.md) уже предлагает создавать пользователей в Dashboard с адресами вида `1001@bistro.local`, и по сообщению владельца приложение работает) |

## 5. Найденные риски

| № | Что | Критичность | Подтверждено |
|---|---|---|---|
| 1 | Миграция 13 пишет в `auth.users` и `auth.identities` напрямую: зависит от версии схемы Auth; вход созданного сотрудника на настоящем GoTrue не проверен | **Высокая** | не проверено; блокирует статус |
| 2 | Токен-колонки, которых не задаёт 13 (`email_change_token_current`, `phone_change`, `phone_change_token`, `reauthentication_token`): при отсутствии значения по умолчанию остаются NULL → вход может падать | Высокая, если схема старая | в модели — да; на GoTrue — нет |
| 3 | Стоимость bcrypt 6 вместо стандартной 10 (`gen_salt('bf')` без параметра) | Средняя (слабее устойчивость хешей к подбору) | да, `$2a$06$` |
| 4 | Длина пароля проверяется в символах, bcrypt учитывает 72 **байта**: кириллический пароль из 40 символов принимается, окончание после 72-го байта не влияет на проверку. Клиентская библиотека или сервер, отвергающие пароль длиннее 72 байт, дадут отказ входа | Средняя | да (pgcrypto); поведение GoTrue — нет |
| 5 | Отключённый сотрудник сохраняет возможность получить токен напрямую через Auth, мимо приложения; данные закрыты RLS и функциями. Сессии и токены обновления не отзываются при отключении и смене пароля | Низкая–средняя | да (HTTP и SQL); на GoTrue — нет |
| 6 | Пользователь, вставленный в `auth.users` SQL-ом без токен-колонок, не входит (в модели) | Информационная | в модели |
| 7 | Состояние при сбое: записи `auth.users`, `auth.identities`, `profiles` создаются в одной функции, откат целиком | — (подтверждено, не риск) | да |
| 8 | `employee_login_email` открыта `anon` по замыслу: можно узнать, существует ли активный сотрудник с кодом, и получить его служебный email | Низкая (известно, ограничение частоты — на стороне Auth) | да |

## 7. Что нельзя проверить без настоящего Supabase

- Принимает ли GoTrue вашей версии запись, созданную `admin_create_staff` (все NOT NULL и значения по умолчанию, токен-колонки).
- Реальный вход созданного сотрудника (`/token?grant_type=password`), повторный вход, выдача и обновление токенов, ответ на неверный пароль и на NULL в токенах.
- Нужна ли запись в `auth.identities` для входа по паролю и для обновления пользователя.
- Принимает ли GoTrue адрес `<uuid>@bistro.local` и хеш `$2a$06$`, и как он относится к паролю длиннее 72 байт.
- Действие сессий и токенов обновления после отключения сотрудника и смены пароля.
- Ограничение частоты запросов входа и поведение `employee_login_email` под нагрузкой.
- Владелец объектов и права по умолчанию (`postgres` в Supabase не суперпользователь), доступ роли к схеме `auth`.
