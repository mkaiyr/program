## 1. Неоднозначное встраивание кассира в `load_orders`

**Описание.** Список заказов запрашивал кассира встраиванием `cashier:profiles(full_name)`, не указывая, по какому
внешнему ключу связаны `orders` и `profiles`.

**Как проявлялось.** Известно только, как запрос выглядел в `HEAD`: `db.py`, `load_orders` —
`.select("id, created_at, total, status, cashier:profiles(full_name), order_items(...)")`
(`git show HEAD:db.py`). Наблюдавшегося на Supabase сообщения об ошибке нет: приложение с реальным PostgREST
в этой работе не запускалось на базе с миграцией 10.
**Предположение:** на базе с применённой миграцией 10 PostgREST отвечает на такой запрос ошибкой неоднозначной связи
(код `PGRST201`), и окно «Заказы» показывает «Не удалось загрузить заказы. Код ошибки: PGRST201». Поведение PostgREST
локально **не воспроизводилось** (его в окружении нет), оно выведено из его документированного правила: встраивание
по имени таблицы требует единственной связи между таблицами.

**Техническая причина (подтверждена).**
- До миграции 10 у `orders` был один внешний ключ на `profiles` — `orders_cashier_id_fkey`.
- Миграция 10 добавила `orders.deleted_by uuid references public.profiles (id)` (`sql/10_order_deletion.sql`, строка 67) — второй ключ,
  `orders_deleted_by_fkey`.
- Миграция 11 добавила третий — `orders_voided_by_fkey`.
- Список внешних ключей `orders` на локальной базе после 01–14 (запрос `pg_constraint`, 2026-11-11):
  `orders_cashier_id_fkey`, `orders_deleted_by_fkey`, `orders_shift_id_fkey`, `orders_voided_by_fkey`.
  Три из них ведут на `profiles` (кроме `orders_shift_id_fkey` → `cash_shifts`).

**Исправление.** Встраивание теперь называет ключ: `cashier:profiles!orders_cashier_id_fkey(full_name)`; для аннулировавшего —
`voider:profiles!orders_voided_by_fkey(full_name)`. Исправлены оба набора колонок: новый (`ORDER_COLUMNS`) и прежний,
которым запрос пользуется, если колонок миграции 11 ещё нет (`ORDER_COLUMNS_OLD`). Имена ключей совпадают с теми, что
Postgres создаёт для `column references table` (`<таблица>_<столбец>_fkey`) и подтверждены запросом выше.

**Затронутые файлы.** `db.py` (`Database.ORDER_COLUMNS_OLD`, `Database.ORDER_COLUMNS`, `load_orders`).

**Проверка после исправления.**
- Имена ключей на целевой базе:
  ```sql
  select conname from pg_constraint
   where conrelid = 'public.orders'::regclass and contype = 'f' order by 1;
  ```
  Ожидаются `orders_cashier_id_fkey` и (после 11) `orders_voided_by_fkey`.
- Ручная проверка на Supabase с применёнными 10 и 11: открыть «Заказы» (кассир) и «История заказов» (администратор) —
  список с именем кассира загружается без «Код ошибки: PGRST201».
- **Чего нет:** автоматического теста, который бы проверял строку `select`. Тесты работают на заглушке клиента
  (`MagicMock`) и не видят ни PostgREST, ни текст запроса; `tests/test_new_modules.py::test_load_orders_filters_and_old_schema`
  проверяет фильтры и откат к старой схеме, но не встраивание. Реальная проверка исправления возможна только на Supabase.

## 2. Обрезанные подписи и кнопки в новых экранах

**Описание.** Первая версия новых экранов содержала элементы, которым не хватало места при допустимых размерах окна.
Ошибки жили в коде этого пакета и были найдены до поставки; в выпущенном приложении их не было.

**Как проявлялось.** Программная проверка (обход виджетов: ширина `winfo_width` меньше запрошенной `winfo_reqwidth`, выход
за границу окна; размеры окна 960×600, 1100×680, 1250×760, 1600×900) сообщила:

| Размер окна | Экран | Элемент (ширина фактическая < запрошенная) |
|---|---|---|
| 1100×680 | главная | подпись карточки «Активных сотрудников» (132 < 151) |
| 1100×680, 1250×760 | касса | кнопка «Очистить» (51 < 163 и 111 < 163) |
| 1250×760 | касса | подсказка «Enter — добавить по коду» (90 < 166) |
| 960×600 | касса | подсказка «Enter — по коду» (61 < 104) |
| 1100×680 | касса | кнопка «✕» поиска (48 < 52) |
| 1100×680, 1250×760 | история заказов | кнопки «Найти» (58 < 133) и «Сбросить» (63 < 133) |

**Техническая причина.** Кнопки корзины использовали `Big.TButton` (шрифт 16 pt, отступы 18×14) — вчетвером они не
помещались в колонку корзины шириной 380; строка фильтров истории была одной строкой из шести полей; текст
подсказки поиска и заголовок карточки были длиннее отведённого места.

**Исправление.**
- Новый стиль `Touch.TButton` (шрифт 13 pt bold, отступы 14×12) для «−», «+», «Удалить», «Очистить»; минимальная ширина
  колонки корзины 470.
- Подсказку поиска убрали, подпись поля — «Поиск (код + Enter):»; поле поиска сужено; кнопка «✕» шире.
- Заголовок карточки — «Сотрудники», пояснение «активных; всего N».
- Фильтры истории разнесены на две строки (номер и дата; статус, аннулирование, «Найти», «Сбросить»).

**Затронутые файлы.** `ui_theme.py` (`Touch.TButton`), `ui_order.py`, `ui_orders.py`, `ui_admin_panels.py`.

**Проверка после исправления.** Повторный обход при тех же размерах не нашёл замечаний; `python3.12 -m pytest -q` проходит.
Скрипты обхода были временными и **в репозиторий не входят** — для повторной проверки их надо написать заново:
для каждого раздела `AdminShell` и для `OrderFrame` при перечисленных размерах сравнить `winfo_width()` кнопок и подписей
с `winfo_reqwidth()`. Вид интерфейса по снимкам экрана не проверялся (среда не дала снимать экран).

## Не ошибки: намеренные изменения поведения

Эти изменения могут выглядеть как поломки, поэтому описаны отдельно.

| Что | Почему изменилось |
|---|---|
| Касса показывает итог на 10% больше суммы позиций | Надбавка 10% — требование пакета; расчёт на сервере (`place_order`) |
| Тесты корзины ожидают другие суммы (3 190.50 ₸, 770.50 ₸, 3 190 ₸, 770 ₸) и `expected_total` у заглушек `create_order` | Те же причины; ожидания заменены явными числами, а не вычислением тем же кодом |
| `sql/tests/09_station_menu_checks.sql` падала: «сумма заказа должна быть 2 × 450.50 + 600.00» | Проверка 09 ожидала итог без надбавки. После миграции 11 `create_order` добавляет надбавку. Проверка изменена: подытог = 1501.00, итог = подытог + `service_amount`, если он есть в ответе (работает и до 11) |
| `test_app_routes_by_role` ожидает `AdminShell` для администратора | Администратор теперь входит в оболочку, а не на экран кассы |

## Известные нерешённые проблемы (не исправления)

- **Повторный запуск 08 откатывает 11.** Миграция 08 пересоздаёт `create_order` и `_station_orders` прежними текстами.
  Подтверждено локально 2026-11-11: после 08 `create_order` больше не вызывает `place_order`; после 09 и 11 снова вызывает.
  Порядок восстановления — [DATABASE.md](DATABASE.md#повторный-запуск). Старые файлы не получили предусловий против этого
  (правило «добавлять признак в предусловия старых миграций» из [DEVELOPMENT.md](DEVELOPMENT.md#правила) здесь осознанно не применено,
  по образцу 09; это решение нужно подтвердить).
- **Прямая запись в `auth.users` (миграция 13) не проверена на GoTrue.** Локальная проверка использует таблицы `auth.users` и
  `auth.identities`, созданные эмуляцией, а не настоящий GoTrue. Работа входа созданного сотрудника на Supabase — предположение,
  подтверждается проверкой `sql/tests/13_staff_checks.sql` и ручным входом на тестовом проекте.
