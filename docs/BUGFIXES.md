## 1. Неоднозначное встраивание кассира в `load_orders`

**Описание.** Список заказов запрашивал кассира встраиванием `cashier:profiles(full_name)`, не указывая, по какому
внешнему ключу связаны `orders` и `profiles`.

**Как проявлялось.** В `HEAD` запрос выглядел так: `db.py`, `load_orders` —
`.select("id, created_at, total, status, cashier:profiles(full_name), order_items(...)")` (`git show HEAD:db.py`).
Наблюдавшегося пользователями или на облачном Supabase сообщения об ошибке нет. Воспроизведено на **локальном стенде**
(PostgreSQL 17 + PostgREST **16.5** + `supabase-py`/`postgrest-py` **2.33.0**, 2026-11-14; стенд не является Supabase —
версия PostgREST в облаке может отличаться и на нём это **не проверялось**):
- До миграции 10 (один ключ `orders → profiles`) запрос без указания ключа и запрос с ключом — оба `HTTP 200`.
- После миграции 10 запрос без указания ключа — **`HTTP 300`**, тело ответа PostgREST — `{"code":"PGRST201", …}` с перечнем
  связей; запрос с `profiles!orders_cashier_id_fkey` — `HTTP 200`.
- `postgrest-py` 2.33.0 ответ с кодом 300 как ошибку PostgREST **не разбирает**: исключение `APIError` имеет `code = 300`,
  `message = 'JSON could not be generated'`, `hint = 'Refer to full message for details'`, а тело ответа (с `PGRST201`) лежит
  в `details` в виде строки. То есть в проверенном сценарии SDK **не** возвращает код `PGRST201` в поле `code`.
- Что увидел бы сотрудник: `db._api_error` для ошибки такого вида даёт «Не удалось загрузить заказы. Код ошибки: **300**.»
  (проверено подачей `APIError` той же формы в `_api_error`; полностью старый код `load_orders` до исправления на стенде
  не запускался).

**Техническая причина (подтверждена на локальном стенде и по схеме).**
- До миграции 10 у `orders` был один внешний ключ на `profiles` — `orders_cashier_id_fkey`.
- Миграция 10 добавила `orders.deleted_by uuid references public.profiles (id)` (`sql/10_order_deletion.sql`, строка 67) — второй ключ,
  `orders_deleted_by_fkey`.
- Миграция 11 добавила третий — `orders_voided_by_fkey`.
- Список внешних ключей `orders` на локальной базе после 01–14 (запрос `pg_constraint`, 2026-11-11):
  `orders_cashier_id_fkey`, `orders_deleted_by_fkey`, `orders_shift_id_fkey`, `orders_voided_by_fkey`.
  Три из них ведут на `profiles` (кроме `orders_shift_id_fkey` → `cash_shifts`).

**Исправление.** Встраивание теперь называет ключ: `cashier:profiles!orders_cashier_id_fkey(full_name)`; для аннулировавшего —
`voider:profiles!orders_voided_by_fkey(full_name)`. Исправлены оба набора колонок: новый (`ORDER_COLUMNS`) и прежний,
которым запрос пользуется, если колонок миграции 11 ещё нет (`ORDER_COLUMNS_OLD`). Имена ключей совпадают с теми, что
Postgres создаёт для `column references table` (`<таблица>_<столбец>_fkey`) и подтверждены запросом выше.

**Затронутые файлы.** `db.py` (`Database.ORDER_COLUMNS_OLD`, `Database.ORDER_COLUMNS`, `load_orders`).

**Проверка после исправления.**
- Имена ключей на целевой базе:
  ```sql
  select conname from pg_constraint
   where conrelid = 'public.orders'::regclass and contype = 'f' order by 1;
  ```
  Ожидаются `orders_cashier_id_fkey` и (после 11) `orders_voided_by_fkey`.
- Ручная проверка на облачном Supabase с применёнными 10 и 11: открыть «Заказы» (кассир) и «История заказов» (администратор) —
  список с именем кассира загружается без сообщения «Не удалось загрузить заказы. Код ошибки: 300.» (а не «…PGRST201»).
- Проверено на локальном стенде (не Supabase): ровно тот `select`, который строит `db.load_orders` (с `ORDER_COLUMNS`), через
  `supabase-py` возвращает заказы с именем кассира (`HTTP 200`); окна «Заказы» кассира и «История заказов» администратора
  в сценариях копии приложения загружаются без ошибок.
- **Чего нет:** автоматического теста в репозитории, который бы проверял строку `select`. Тесты работают на заглушке клиента
  (`MagicMock`) и не видят ни PostgREST, ни текст запроса; `tests/test_new_modules.py::test_load_orders_filters_and_old_schema`
  проверяет фильтры и откат к старой схеме, но не встраивание. Стендовые проверки лежат вне репозитория
  (`~/cashier_pgrst_test/scripts/`). Проверка на облачном Supabase остаётся за вами.

## 2. Обрезанные подписи и кнопки в новых экранах

**Описание.** Первая версия новых экранов содержала элементы, которым не хватало места при допустимых размерах окна.
Ошибки жили в коде этого пакета и были найдены до поставки; в выпущенном приложении их не было.

**Как проявлялось.** Программная проверка (обход виджетов: ширина `winfo_width` меньше запрошенной `winfo_reqwidth`, выход
за границу окна; размеры окна 960×600, 1100×680, 1250×760, 1600×900) сообщила:

| Размер окна | Экран | Элемент (ширина фактическая < запрошенная) |
|---|---|---|
| 1100×680 | главная | подпись карточки «Активных сотрудников» (132 < 151) |
| 1100×680, 1250×760 | касса | кнопка «Очистить» (51 < 163 и 111 < 163) |
| 1250×760 | касса | подсказка «Enter — добавить по коду» (90 < 166) |
| 960×600 | касса | подсказка «Enter — по коду» (61 < 104) |
| 1100×680 | касса | кнопка «✕» поиска (48 < 52) |
| 1100×680, 1250×760 | история заказов | кнопки «Найти» (58 < 133) и «Сбросить» (63 < 133) |

**Техническая причина.** Кнопки корзины использовали `Big.TButton` (шрифт 16 pt, отступы 18×14) — вчетвером они не
помещались в колонку корзины шириной 380; строка фильтров истории была одной строкой из шести полей; текст
подсказки поиска и заголовок карточки были длиннее отведённого места.

**Исправление.**
- Новый стиль `Touch.TButton` (шрифт 13 pt bold, отступы 14×12) для «−», «+», «Удалить», «Очистить»; минимальная ширина
  колонки корзины 470.
- Подсказку поиска убрали, подпись поля — «Поиск (код + Enter):»; поле поиска сужено; кнопка «✕» шире.
- Заголовок карточки — «Сотрудники», пояснение «активных; всего N».
- Фильтры истории разнесены на две строки (номер и дата; статус, аннулирование, «Найти», «Сбросить»).

**Затронутые файлы.** `ui_theme.py` (`Touch.TButton`), `ui_order.py`, `ui_orders.py`, `ui_admin_panels.py`.

**Проверка после исправления.** Повторный обход при тех же размерах не нашёл замечаний; `python3.12 -m pytest -q` проходит.
Скрипты обхода были временными и **в репозиторий не входят** — для повторной проверки их надо написать заново:
для каждого раздела `AdminShell` и для `OrderFrame` при перечисленных размерах сравнить `winfo_width()` кнопок и подписей
с `winfo_reqwidth()`. Вид интерфейса по снимкам экрана не проверялся (среда не дала снимать экран).

## 3. Кнопки категорий на кассе уходят за край колонки

**Описание.** Кнопки категорий на кассе выкладывались в одну строку (`pack(side="left")`). Число категорий определяется меню, поэтому при большом числе категорий (в ТЗ архива —
«Все» и семь категорий) правые кнопки не помещались.

**Как проявлялось (измерено).** Для восьми кнопок рамка запрашивала 728 px ширины, а колонка каталога давала 446 px при окне 960 px, 586 px при 1100 px и 750 px при 1280 px:
правый край последней кнопки оказывался на 738 px — при окнах 960 и 1100 px правые кнопки обрезались колонкой (при 1280 px помещались). Жалоб пользователей на это в истории нет: проблема
найдена проверкой размеров при подготовке интерфейса архива; при небольшом числе категорий (меньше пяти-шести коротких названий) кнопки помещались.

**Причина (подтверждена измерением).** Одна строка без переноса, ширина зависит от числа и длины названий категорий.

**Исправление.** `OrderFrame._reflow_chips` раскладывает кнопки сеткой и переносит на новую строку по ширине рамки; вызывается при построении кнопок и при изменении ширины (`<Configure>`).
При 960 px — две строки, при 1600 px — одна.

**Файлы.** `ui_order.py`, `tests/test_menu_archive_ui.py` (`test_many_categories_wrap_instead_of_overflowing`).

**Проверка.** Измерение при 960×600, 1100×680, 1280×800, 1400×850, 1600×900 и при запуске без заданного размера: правый край кнопок не выходит за рамку, кнопка заказа видна.

## 4. Бесконечный цикл `<Configure>` при переносе кнопок категорий

**Описание.** Первая версия переноса кнопок (п. 3) вызывала зацикливание: перекладка кнопок меняла событие `<Configure>` рамки, обработчик снова перекладывал кнопки. Ошибка жила только
в черновом коде этого пакета и в поставку не попала.

**Как проявлялось.** Набор тестов падал с `Fatal Python error: Segmentation fault` в `tkinter.update` (в тесте `test_many_categories_wrap_instead_of_overflowing`, воспроизводилось
при каждом запуске). Трассировка вызовов `_reflow_chips` показала десятки тысяч вызовов и колебание ширины рамки между 378 и 400 px, раскладки — между двумя вариантами.

**Техническая причина.** Ширина рамки с кнопками определялась её содержимым (рамка подстраивалась под кнопки), а раскладка — шириной рамки. Защита «не перекладывать, если раскладка
та же» не помогала, потому что раскладка менялась на каждом шаге. Что именно приводило к падению процесса (переполнение стека при рекурсии обработчиков), — **вывод**
из трассировки и вида падения; прямо подтверждено только колебание и рост числа вызовов.

**Исправление.** Рамка кнопок создаётся с `grid_propagate(False)` и фиксированной нулевой запрошенной шириной; её высоту `_reflow_chips` задаёт сам по числу строк.
Ширина больше не зависит от кнопок, раскладка сходится.

**Файлы.** `ui_order.py` (`OrderFrame.__init__`, `_reflow_chips`).

**Проверка.** Тест `test_many_categories_wrap_instead_of_overflowing` проходит; трассировка — 9 вызовов вместо десятков тысяч; в живом окне без заданного размера
число перекладок после запуска, увеличения и уменьшения окна — 3, 7 и 11 в сумме, раскладка стабильна. Весь набор — 365 passed.

## 5. SQL-проверка 14 зависела от времени создания других заказов

**Описание.** `sql/tests/14_reports_checks.sql` брал начало периода отчёта как `clock_timestamp() − 1 секунда`.

**Как проявлялось.** На только что созданной базе проверка 14 упала («сводка неверна», 3 заказа вместо 2): в период попал заказ, созданный секундой раньше при подготовке данных.
На базе со старыми заказами проверка проходила.

**Причина (подтверждена).** Внутри транзакции `now()` равен началу транзакции, а `clock_timestamp()` — текущему моменту; окно со смещением в секунду зависело от других заказов, созданных рядом по времени.

**Исправление.** Начало периода — `now()` (начало транзакции, в которой создаются тестовые заказы), без смещения. То же сделано в `15_menu_item_archive_checks.sql`.
Миграция 14 не менялась — ошибка была в тесте, не в SQL-функции.

**Файлы.** `sql/tests/14_reports_checks.sql`, `sql/tests/15_menu_item_archive_checks.sql`.

**Проверка.** Проверки 14 и 15 проходят на новой и на «грязной» базах.

## Известные нерешённые проблемы (не исправления)

- **Повторный запуск 09 или 14 откатывает 15.** 09 возвращает `station_menu` без архивных блюд (подтверждено локально 2026-11-14), 14 — `admin_report` без снимка категории.
  После любого из них нужно снова запустить 15; порядок — [DATABASE.md](DATABASE.md#повторный-запуск). Предусловий в старых файлах нет (как и в случае с 11).
- **Число заказов в подтверждении удаления блюда может быть меньше итогового.** `Database.count_menu_item_orders` читает заказы через RLS, который скрывает заказы из «Удалённых заказов»;
  точное число возвращает сервер после удаления (`orders_count`). Решение об удалении сервер принимает сам.
- **Включить наличие архивного блюда через старые функции нельзя, но сообщение общее на сервере.** `admin_set_menu_item_available` вернёт нарушение ограничения (`23514`);
  приложение переводит его в «Блюдо в архиве — сначала восстановите его», а в редакторе архивные блюда не показываются.

- **Повторный запуск 08 откатывает 11.** Миграция 08 пересоздаёт `create_order` и `_station_orders` прежними текстами.
  Подтверждено локально 2026-11-11: после 08 `create_order` больше не вызывает `place_order`; после 09 и 11 снова вызывает.
  Порядок восстановления — [DATABASE.md](DATABASE.md#повторный-запуск). Старые файлы не получили предусловий против этого
  (правило «добавлять признак в предусловия старых миграций» из [DEVELOPMENT.md](DEVELOPMENT.md#правила) здесь осознанно не применено,
  по образцу 09; это решение нужно подтвердить).
- **Прямая запись в `auth.users` (миграция 13) не проверена на GoTrue.** Локальная проверка использует таблицы `auth.users` и
  `auth.identities`, созданные эмуляцией, а не настоящий GoTrue. Работа входа созданного сотрудника на Supabase — предположение,
  подтверждается проверкой `sql/tests/13_staff_checks.sql` и ручным входом на тестовом проекте.
