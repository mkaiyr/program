# Единый каталог, заказы и склад — финальная схема для согласования (версия 2)

Дата: 2026-11-25. Заменяет раздел решений документа `UNIFIED_CATALOG_INVENTORY_DESIGN.md` (он остаётся как история этапа A). **Ничего не применялось:** ни одна база не создавалась и не менялась, SQL не выполнялся, миграции не созданы — только черновики для ревью в `docs/drafts/18…23_*.sql.draft`. Production не затрагивался.

Решения владельца, на которых построена схема: единый каталог для сайта и кассы; неподтверждённые цены не публикуются; при заполненной технологической карте и нехватке продуктов продажа блокируется; без карты — ничего не списываем, показываем предупреждение; заказ сайта списывает склад **при принятии** сотрудником; отмена после начала приготовления не возвращает продукты автоматически; надбавка на заказы сайта автоматически не добавляется; роли `stockkeeper`/`manager` пока не создаются.

## 1. Схема (что где живёт)
```
menu_items (есть)            ── единственный источник блюда: id, code, name, category, price, is_available, station, approved/archived
  ├─ menu_item_public (18)   ── 1:1 расширение для сайта: slug, описание, вес, фото, порядок, published, подтверждённая цена
  ├─ menu_item_ingredients (18) → ingredients (18) → ingredient_allergens (18) → allergens (18)   ── описательный состав и аллергены
  └─ recipe_lines (21)       ── технологическая карта: продукт склада + количество + единица (пусто = «нет карты»)
stock_products (19)          ── продукты: unit, purchase_price, min_stock, stock (check ≥ 0)
  └─ stock_movements (19)    ── журнал (только добавление): receipt | sale | cancel | return | loss | count
suppliers (19) ─ stock_receipts + lines (20) ── поступления (черновик → подтверждено)
stock_counts + lines (22)    ── инвентаризации
orders (есть, +source, +confirmed_at (23)) ─ order_items (снимки, есть) ─ order_stations (есть)
  ├─ order_stock_ops (21)    ── что склад сделал по заказу: 'sale' и 'cancel' — по одной записи (защита от повторов в БД)
  ├─ order_customers (23)    ── персональные данные клиента сайта (без прав у клиентов)
  └─ order_tracking (23)     ── хеш токена отслеживания
```
Принципы: одна таблица заказов и один поток для кассы и сайта; остаток меняет только `_stock_post` (блокирует строку продукта, проверяет, пишет движение); клиенты не имеют прав на таблицы — только на функции; все склад-таблицы с RLS без политик.

## 2. Контракты API
Ошибки — как в проекте: `message` = код, `detail` = подробности; приложение переводит в понятный текст.

### Сайт (роль `anon`) — только две функции
| Функция | Вход | Ответ | Ошибки |
|---|---|---|---|
| `public_menu()` | — | каталог в формате `docs/contracts/public_catalog.md` (только опубликованные, подтверждённая цена, неархивные; без закупочных данных) | — |
| `web_place_order(request_id uuid, items [{slug, quantity}], customer {name, phone, fulfillment, address?, comment?, pay_method})` | цены сервер берёт сам | `{order_id, total, tracking_token}` (токен — один раз); повтор → `duplicate: true` без токена; **склад не меняется** | `INVALID_REQUEST`, `MENU_CHANGED` (detail — названия) |
| `web_order_status(token text)` | токен | статус, состав, итог; **без** телефона, адреса, комментария | пусто, если токен неверный |

### Касса и администратор (роль `authenticated`, права проверяются внутри)
| Функция | Кто | Назначение / ответ | Ошибки |
|---|---|---|---|
| `place_order(...)` (есть, не меняется) | кассир, админ | заказ кассы; склад списывается триггером в той же транзакции | + `INSUFFICIENT_STOCK` (detail: «Мясо: нужно 0.3 кг, есть 0.2 кг») |
| `stock_check_items(items)` | кассир, админ | до оформления: `{blocked, message, no_recipe[]}` — понятная причина блокировки и позиции без карты | — |
| `order_stock_info(order_id)` | кассир, админ | `{deducted, warning{no_recipe[]}, auto_cancelled}` | `ORDER_NOT_FOUND` |
| `web_order_accept(order_id)` | кассир, админ | принять заказ сайта: подтверждение + станции + списание атомарно; повтор → `duplicate: true` | `ORDER_NOT_FOUND`, `INSUFFICIENT_STOCK` (заказ остаётся непринятым) |
| `void_order(...)` (есть) | кассир (свои), админ | аннулирование; до начала приготовления триггер возвращает всё списанное один раз | — |
| `stock_return_selected(order_id, ref uuid, lines, reason)` | админ | вернуть пригодные продукты после начала приготовления / возврат готового заказа | `REASON_REQUIRED`, `RETURN_EXCEEDS` |
| `stock_write_off(ref uuid, product_id, qty, reason, order_id?)` | админ | потери; не больше остатка | `INVALID_WRITE_OFF`, `INSUFFICIENT_STOCK` |
| `admin_set_menu_item_public / admin_confirm_menu_price / admin_publish_menu_item` | админ | данные для сайта, подтверждение цены, публикация | `PRICE_NOT_CONFIRMED` |
| `admin_save_stock_product / stock_products_list / stock_product_history / admin_save_supplier / supplier_summary` | админ | справочники, остатки, история, сумма закупок | `UNIT_LOCKED`, `PRODUCT_NOT_FOUND` |
| `admin_create_receipt / admin_confirm_receipt` | админ | поступление (повтор формы и повторное подтверждение безопасны) | `INVALID_LINES`, `RECEIPT_NOT_FOUND` |
| `admin_set_recipe(item_id, lines)` | админ | технологическая карта | — |
| `admin_create_count / admin_set_count_line / admin_confirm_count / stock_ledger_check` | админ | инвентаризация; сверка журнала и остатков | `REASON_REQUIRED`, `NEGATIVE_ACTUAL` |

## 3. Матрица прав (роли — только существующие; `stockkeeper`/`manager` позже, отдельным разрешением)
| Действие | cashier | kitchen / bar | admin | anon (сайт) | Будущие `stockkeeper` | Будущий `manager` |
|---|---|---|---|---|---|---|
| Видеть меню и доступность | да | свои станции (как сейчас) | да | публичное, опубликованное | да | да |
| Видеть складской статус блюда и предупреждения (`stock_check_items`, `order_stock_info`) | **да** | нет | да | нет | да | да |
| Видеть остатки, историю движения | нет | нет | да | нет | да | да |
| Редактировать закупочные цены, технологические карты, остатки, поставщиков | **нет** | нет | да | нет | остатки/поступления/инвентаризация — да; цены закупки — нет | отчёты и утверждение цен — да, склад — нет |
| Поступления, инвентаризация, потери, возврат продуктов | нет | нет | да | нет | да | просмотр |
| Подтверждать цены и публиковать блюда на сайте | нет | нет | да | нет | нет | да (будущее) |
| Принимать заказы сайта | да | нет | да | нет | нет | да |
| Создавать заказ с сайта / смотреть по токену | нет | нет | нет | да (только свой по токену) | — | — |
Проверка прав — на сервере (внутри функций и RLS); скрытые кнопки интерфейса — только удобство.

## 4. Сценарии и складские эффекты
| # | Сценарий | Что происходит | Склад |
|---|---|---|---|
| 1 | **Поступление** | админ создаёт черновик (поставщик, строки, цены) → подтверждает | остатки растут один раз; повторное подтверждение/повтор формы — без эффекта; движения `receipt` |
| 2 | **Продажа в кассе, карта заполнена, продуктов хватает** | `place_order` → триггер списывает по карте | движения `sale`, остатки уменьшены; всё в одной транзакции |
| 3 | **Продажа, карта заполнена, не хватает** | кассир сразу видит причину (`stock_check_items`); сервер блокирует `INSUFFICIENT_STOCK`; заказ **не создаётся** | без изменений |
| 4 | **Продажа, карты нет** | заказ проходит; `warning.no_recipe`; кассир видит «склад не проверен (нет технологической карты)» | **ничего не списывается**; доступность склада не подтверждена |
| 5 | **Заказ сайта** | клиент создаёт заказ (цены от сервера) → ожидает принятия | **не меняется**; при принятии (`web_order_accept`) списание как в п. 2–4; повторное принятие — без эффекта; при нехватке принятие откатывается |
| 6 | **Отмена до начала приготовления** (`status = 'accepted'`) | `void_order` → триггер | автоматически возвращается всё списанное, один раз (`cancel`) |
| 7 | **Отмена после начала приготовления** | заказ аннулируется | **склад не меняется**; администратор отдельно: `stock_return_selected` (что пригодно) и/или `stock_write_off` (что потеряно), с причиной и количеством |
| 8 | **Возврат готового заказа** | как п. 7 | автоматического возврата нет; только явные операции; сумма возвратов ≤ списанного |
| 9 | **Потери** (порча, брак) | `stock_write_off` | движение `loss`; не больше остатка; причина обязательна; повтор по ключу без эффекта |
| 10 | **Инвентаризация** | создаётся с расчётными остатками → вводятся факт и причины → подтверждается | корректирующие движения `count` (факт − текущий остаток); расхождение без причины запрещено; повтор — без эффекта |
Эталонная модель (`inventory_model.py`, `docs/contracts/inventory_vectors.json`, 19 сценариев + 26 подтестов) уже проверяет эти правила на Python; те же векторы должны пройти SQL-функции на тестовой БД.

## 6. Открытые вопросы к ревью (отмечены в черновиках «ВОПРОС РЕВЬЮ»)
1. Слаг категории: на сайте id категорий — слаги, в `menu_categories` только название (18).
2. `cashier_id` nullable и RLS/отчёты для заказов сайта (23).
3. Определение «приготовление началось» = `orders.status <> 'accepted'`; подтвердить на тестовой БД (21).
4. Начальные остатки вносить документом инвентаризации, иначе журнал не сойдётся (22).
5. Нужны ли лимиты на анонимный `web_place_order` (спам) и капча (23).
6. Должен ли `available` на сайте отражать нехватку продуктов автоматически (сейчас — нет: только признак администратора; склад блокирует при принятии).
