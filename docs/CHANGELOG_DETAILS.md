## 1. Разделение кухни и бара

**Проблема.** Был один экран кухни и один статус на весь заказ. Напитки готовились там же;
бар не мог работать отдельно.
**Причина.** В схеме не было понятия станции ни у позиции меню, ни у позиции заказа.
**Решение.**
- `menu_items.station` (`kitchen` | `bar`) — где готовится позиция; задаётся в «Управлении меню».
- `order_items.station` — снимок станции на момент продажи, как снимок названия и цены:
  смена станции в меню не переносит уже оформленные позиции.
- `kitchen_orders()` и `bar_orders()` возвращают только позиции своей станции, без цен, сумм
  и кассира; внутренняя `_station_orders(station)` закрыта для клиентов.
- Экран бара — тот же `KitchenFrame` для роли `bar` (`BarFrame`), без вкладки меню.
- Существующие позиции меню и старые заказы получают станцию `kitchen` — поведение не меняется,
  напитки переводятся в бар отдельным шагом.

**Файлы.** `sql/08_bar_stations.sql`, `db.py` (`load_station_orders`, `STATIONS`), `ui_kitchen.py`,
`ui_admin.py`, `main.py`.
**Проверка.** `tests/test_bar_stations.py` (экран бара, поиск, вызовы RPC, маршрутизация);
`sql/tests/08_bar_stations_checks.sql` — смешанный заказ «еда + напиток» виден станциям по частям.
**Ограничения.** Наличие всех блюд, включая напитки, по-прежнему отмечает кухня; у бара вкладки
наличия нет. Модификаторов позиций в модели заказа нет.

## 2. Роли и ограничения доступа

**Проблема.** Нужна роль бармена без доступа к продажам, ценам и чужой станции.
**Причина.** Существующая проверка `is_active_staff()` (кассир и администратор) открывает
`create_order` и чтение меню с ценами — добавлять туда бар нельзя.
**Решение.**
- Отдельная `is_active_bar()`; `bar` добавлен в `profiles_role_check` и в `employee_login_email`.
- 08 заменяет только `profiles_role_check` и только если его фактический набор ролей —
  ровно `{cashier, admin, kitchen}`; уже с `bar` — ничего не делает; иначе останавливается.
  Ограничения не удаляются по совпадению слова `role`, проверка `LIKE '%bar%'` не используется.
- `set_station_status`: кухня — только `kitchen`, бар — только `bar` (`STATION_NOT_ALLOWED`).
- Таблица `order_stations` — RLS без политик, прав у клиентов нет.

**Файлы.** `sql/08_bar_stations.sql`, `db.py` (`ALLOWED_ROLES`, `ROLE_TRANSITIONS`), `main.py`.
**Проверка.** `tests/test_bar_stations.py::test_role_set_decision` выполняет регулярные выражения
и наборы ролей из миграции на образцах определения ограничения (в том числе `barista`, другой
порядок, лишние условия); SQL-проверка 08 — бармен не читает таблицы, не вызывает функции кухни,
кассы и администратора, не меняет кухонную часть, неактивный бармен не входит.
**Ограничения.** Формат вывода `pg_get_constraintdef` на реальной базе не проверен (при отличии
миграция остановится). Владельцы функций и таблиц должны совпадать — проверяется SQL-тестом.

## 3. Готовность заказа по всем станциям

**Проблема.** Бар мог бы отметить «Готов» смешанный заказ, пока кухня ещё готовит; обычный переход
администратора «Готов» молча отмечал готовыми все станции.
**Решение.**
- `orders.status` «Принят / Готовится / Готов» вычисляет `_refresh_order_status` из `order_stations`:
  «Готов» — только когда готовы все станции.
- `set_order_status` разрешает только выдачу `ready → completed` (кассир — свои, администратор — любые).
- Принудительная готовность — отдельная `admin_force_order_ready` (только администратор, только из
  «Принят»/«Готовится»), в интерфейсе — кнопка «Готов принудительно» с подтверждением.
- Блокировка строки заказа (`for update`) — станции одного заказа не пересчитывают статус одновременно.

**Файлы.** `sql/08_bar_stations.sql`, `db.py` (`force_order_ready`, `set_station_status`), `ui_orders.py`.
**Проверка.** `tests/test_bar_stations.py` (кнопка принудительной готовности, права по ролям);
SQL-проверка 08 — готовый напиток оставляет смешанный заказ «Готовится», обе станции → «Готов»,
выдача неготового заказа отклоняется, принудительная готовность отмечает 2 станции.
**Ограничения.** Окно «Заказы» показывает только общий статус, без разбивки по станциям.

## 4. Автообновление экранов кухни и бара (7 секунд)

**Проблема.** Новые заказы появлялись с задержкой (было 15 с); при потере связи окно ошибки
открывалось на каждом срабатывании таймера.
**Причина.** Ошибка фонового обновления обрабатывалась как ошибка ручного действия (`messagebox`).
**Решение.** `AUTO_REFRESH_MS = 7000` через `after()`/`after_cancel()`; при занятом экране
обновление откладывается (не более одного запроса); ошибки автообновления — строка статуса и
`logging.warning`, следующая попытка по таймеру; истёкшая сессия — выход. Ручное «Обновить»,
строка поиска и прокрутка сохраняются.
**Файлы.** `ui_kitchen.py`.
**Проверка.** `tests/test_station_refresh.py`: интервал, отсутствие параллельных запросов, ошибка сети
без окон с восстановлением, ошибка до первой успешной загрузки, ручная ошибка с окном, выход по
истёкшей сессии.
**Ограничения.** Пока на экране открыто модальное окно ручной ошибки, обновления ждут его закрытия.

## 5. Звуковой сигнал только о новых заказах

**Решение.** `SeenOrders` хранит ID заказов, уже показанных экрану в этой сессии (не более 5000).
Первая успешная загрузка только запоминает текущие заказы. Далее — один короткий сигнал на
обновление с новыми ID и надпись «Новый заказ № …». Смена статуса, повторная загрузка того же
списка и повторное появление заказа сигнала не дают. Звук — `winsound.MessageBeep` (Windows) или
`bell()` Tk; ошибка звука записывается в лог.
**Файлы.** `ui_kitchen.py` (`SeenOrders`, `play_alert`, `_new_order_ids`).
**Проверка.** `tests/test_station_refresh.py` — первый запуск без сигнала, новый заказ, несколько
сразу (один сигнал), смена статуса, исчез и вернулся, ограничение памяти, сбой звука, путь Windows.
**Ограничения.** Сигнал `bell()` на macOS/Linux зависит от системных настроек звука; заказы,
пришедшие до **первой** успешной загрузки экрана, сигнала не дают.

## 6. Потеря соединения и выход во время запроса

**Проблема.** Ответ сервера, пришедший после выхода из аккаунта, вызывал `invalid command name`.
**Причина.** `deliver` ставил `after(0, …)` на сам экран: при уничтожении экрана Tk удалял команду
либо выполнял обработчик для уже уничтоженных виджетов.
**Решение.** Результат передаётся через корневое окно; `_finish` игнорирует его, если экран закрыт
(`closed`); таймеры отменяются в `destroy()`.
**Файлы.** `ui_kitchen.py`.
**Проверка.** `tests/test_station_refresh.py::test_closed_during_request`,
`test_closed_after_answer_queued` — ошибок в обработчиках Tk нет.
**Ограничения.** Исправление сделано только для экранов кухни и бара. Окна «Заказы» и «Управление
меню» используют прежнюю схему `deliver`: кнопка «Закрыть» на время запроса отключена, но при
выходе из аккаунта посреди запроса в этих окнах та же ошибка Tk возможна (в лог, без падения
приложения).

## 7. Миграция 07 — коды позиций меню

**Решение.** `menu_items.code integer NOT NULL UNIQUE` (1…99999999), последовательность с 1001;
`_next_menu_item_code()` пропускает номера, занятые вручную; ручной код — только при создании
(`CODE_TAKEN` при занятом); триггер `CODE_IMMUTABLE` запрещает изменение. Существующим позициям
коды назначаются по порядку `id`; названия, цены, категории и доступность не меняются.
`menu_items.id` и ссылки заказов не меняются. Повторный запуск 07 после 08 останавливается.
**Файлы.** `sql/07_menu_codes.sql`, `db.py`, `ui_admin.py`, `ui_order.py`, `ui_kitchen_menu.py`, `search.py`.
**Проверка.** `tests/test_menu_codes.py`, `tests/test_search_panels.py`;
`sql/tests/07_menu_codes_checks.sql` — уникальность, неизменность, автокод, занятый код, имя без
учёта регистра, повторная отправка заказа, права на последовательность и функции.
**Ограничения.** Номера последовательности при откате не возвращаются (пропуски в нумерации).
Одновременное создание проверено только по устройству (последовательность + блокировка),
не параллельным тестом.
