# Развёртывание миграции 16 (категории меню) в Supabase Cloud

> **Статус.** Миграция 16 и все проверки выполнены **только локально** (PostgreSQL 17 с эмуляцией Supabase). В Supabase Cloud ничего не применялось и не проверялось.
> Это инструкция, а не отчёт о выполнении. Решение о развёртывании принимает владелец проекта.
> Файлы: [sql/16_menu_categories.sql](../sql/16_menu_categories.sql) (миграция), [sql/deploy/16_precheck.sql](../sql/deploy/16_precheck.sql) и
> [sql/deploy/16_postcheck.sql](../sql/deploy/16_postcheck.sql) (проверки «до» и «после», **только чтение**),
> [sql/tests/16_menu_categories_checks.sql](../sql/tests/16_menu_categories_checks.sql) (полная проверка с подменой ролей — **только на тестовом проекте**).

## 0. Главное, что нужно знать до начала

1. **Миграция 16 требует 15, а 15 требует 11–14.** По документации проекта миграции 11–15 на Supabase **не применялись**. Какое состояние на вашем проекте — покажет предпроверка
   (строки со статусом `STOP`). Если 11–15 нет, их нужно применять **раньше и отдельно** (каждую целиком, по порядку, с её проверкой — [DATABASE.md](DATABASE.md), [MIGRATION_TEST_PLAN.md](MIGRATION_TEST_PLAN.md)).
   Это существенно больше, чем одна миграция 16; тогда сначала весь путь проходит тестовый проект.
2. **Миграция меняет данные в одном случае:** если одна категория записана по-разному (регистр, пробелы по краям — «супы» и «Супы»), написания приводятся к самому частому.
   Блюда, цены, доступность, архив и заказы не меняются. Предпроверка показывает, сколько блюд затронет, и перечисляет такие категории (строки 65–66).
3. **Миграция одна транзакция.** При любой ошибке откатывается целиком, и база остаётся как была (подтверждено локально).
4. **Повторный запуск безопасен.**
5. **Поведение меняется для кухни и бара:** повар и бармен больше не могут предложить блюдо в несуществующей категории (`CATEGORY_NOT_FOUND`) — категории создаёт только администратор. Предупредите персонал.
6. Совместимость версий: **новое приложение со старой базой работает** (категории берутся из блюд, раздел «Категории меню» сообщает «не выполнена миграция 16»);
   **старое приложение с новой базой работает**, кроме одного случая — предложение повара или бармена в новой категории покажет «Код ошибки: 23503» вместо понятного текста.
   Поэтому порядок: сначала база, потом обновить приложение на рабочих местах.

## 1. Подготовка

### 1.1. Тестовый проект (обязательно сначала)
Выполните весь порядок из раздела 2 на отдельном тестовом проекте Supabase, **включая** `sql/tests/16_menu_categories_checks.sql` (нужны активные admin, cashier, kitchen, bar; ничего не сохраняет, в конце rollback)
и ручную проверку из раздела 4. На рабочем проекте этот файл **не запускать**: он создаёт и откатывает заказы (тратит номера последовательностей) и открывает смену кассира.

### 1.2. Окно работ
Выберите время без активных продаж: миграция идёт доли секунды, но на это время блокирует запись в `menu_items` (добавление внешнего ключа). Закройте окна «Управление меню» на рабочих местах.

### 1.3. Резервные копии (до миграции, сохранить вне Supabase)
1. **Полная копия базы.** План с резервными копиями — Dashboard → Database → Backups (создать/скачать, если доступно на вашем тарифе). Если автокопий нет (бесплатный план) — вручную с вашего компьютера
   (строку подключения возьмите в Dashboard → Project Settings → Database; пароль не вставляйте в чат и файлы проекта):
   ```
   pg_dump "postgresql://postgres:[ПАРОЛЬ]@[ХОСТ]:5432/postgres" --no-owner --schema=public -Fc -f cafe_before_16.dump
   ```
   Проверьте, что файл не пустой: `pg_restore -l cafe_before_16.dump | head`.
2. **Данные, которые меняет миграция 16** (выгрузите в CSV через SQL Editor → Download CSV):
   ```sql
   select id, name, category from public.menu_items order by id;           -- как были категории у блюд
   select pg_get_functiondef('public.admin_rename_category(text,text)'::regprocedure);   -- текущее определение (его заменит 16)
   ```
3. Результат предварительной проверки (раздел 2, шаг 1) — сохранить целиком: строки «Контроль» нужны для сравнения.

## 2. Порядок выполнения на Production (после успешного тестового проекта)

**Шаг 1. Предпроверка (только чтение).** SQL Editor → New query → вставить весь [16_precheck.sql](../sql/deploy/16_precheck.sql) → Run.
- Любая строка `STOP` — **не продолжать** (см. раздел 5). Типично: «нет таблицы/функции — сначала миграции 01–15».
- `WARN` в строках 65–66 нормален: он показывает, какие блюда миграция приведёт к единому написанию; запишите число.
- Запишите строки «Контроль» (70–75): число заказов и позиций, блюд в архиве, хеши.

**Шаг 2. Резервные копии** (пункт 1.3). Не переходить к шагу 3, пока файлы не сохранены.

**Шаг 3. Миграция.** SQL Editor → New query → вставить **весь** [sql/16_menu_categories.sql](../sql/16_menu_categories.sql) → Run **один раз**.
- Редактор может предупредить о «destructive operations»: в файле есть `drop trigger/policy if exists` только для собственных объектов миграции. Подтвердите.
- Ожидаемый результат: `Success`. Если в блоке сообщений есть `Категории: приведено к единому написанию блюд — N`, то N должно совпасть со строкой 65 предпроверки.

**Шаг 4. Проверка после (только чтение).** Вставить весь [16_postcheck.sql](../sql/deploy/16_postcheck.sql) → Run.
- Ни одной строки `FAIL`. Все строки статуса `OK`.
- Строки 74–76: число блюд, хеш блюд и хеш заказов **совпадают** со значениями из предпроверки (строки 60, 74, 75); заказов, позиций и блюд в архиве столько же; число категорий (строка 52) равно строке 62 предпроверки.
- Если API отвечает «Could not find the table … in the schema cache», подождите минуту или выполните `notify pgrst, 'reload schema';`.

**Шаг 5. Security Advisor.** Dashboard → Advisors → Security: новых замечаний по `menu_categories` и новым функциям быть не должно (RLS включена, у функций пустой `search_path`).

**Шаг 6. Приложение.** Обновите файлы приложения на рабочих местах (`db.py`, `ui_*.py`, остальные `.py`). `config.ini` не менять; ключ — только публичный (`sb_publishable_…` / `anon`), секретный и `service_role` приложение не принимает.

## 3. Проверка прав на рабочем проекте

Права проверяются по каталогу PostgreSQL в `16_postcheck.sql` (строки 12–36) без записи. Дополнительно, руками в приложении (раздел 4), от имени реальных сотрудников.
Подмену ролей с записью (`sql/tests/16_menu_categories_checks.sql`) на рабочем проекте не выполняйте — она проверена на тестовом.

Что подтверждено локально по HTTP через PostgREST: администратор и кассир читают справочник; повар и бармен получают пустой список (RLS); никто, включая администратора, не может писать в таблицу напрямую
(403); `anon` — 401; `admin_add_category`, `admin_rename_category`, `admin_delete_category` для кассира, повара и бармена — 403 `ADMIN_REQUIRED`.

## 4. Ручная проверка приложения после миграции

Используйте тестовые названия с префиксом («ТЕСТ-кат …») и удалите их в конце через приложение.
1. **Администратор → «Категории меню».** Список категорий, числа блюд совпадают с «Управлением меню». «Добавить» — «ТЕСТ-кат А» появилась; повтор («тест-кат а») отклонён.
2. «Переименовать» «ТЕСТ-кат А» → «ТЕСТ-кат Б»; блюда, если были, остались. «Удалить» пустой — подтверждение, категория исчезла.
3. Создайте блюдо в «ТЕСТ-кат В», попробуйте удалить категорию — понятный отказ с советом перенести блюда. Перенесите блюдо в другую категорию в редакторе, удалите «ТЕСТ-кат В». Тестовое блюдо заархивируйте и удалите навсегда.
4. **Кассир.** Категории по алфавиту; новая пустая категория видна и показывает «нет доступных блюд»; корзина, поиск, надбавка 10% работают; «Обновить меню» подхватывает новую категорию.
5. **Повар / бармен.** «Предложить позицию» в существующей категории — принимается; в несуществующей — «Такой категории нет…».
6. **SQL.** `insert into public.menu_categories (name) values ('ТЕСТ-кат SQL');` → «Обновить» в разделе «Категории меню» и на кассе → появилась; удалить из приложения.
7. История заказов, отчёт «Статистика» и экраны кухни и бара открываются, суммы прежние.

## 5. Если что-то пошло не так

**Миграция завершилась ошибкой (шаг 3).** Транзакция откатилась, база не изменена. Проверьте: `select to_regclass('public.menu_categories');` — должно быть `NULL`. Скопируйте полный текст ошибки.

| Ошибка | Причина и действие |
|---|---|
| `Сначала выполните миграции 01–15. Не найдено: …` | на проекте нет предыдущих миграций; применить их по порядку (раздел 0, п. 1) |
| `permission denied for table users` / `must be owner` | миграцию запускает не владелец (`postgres`); запускать из SQL Editor под владельцем проекта |
| `could not obtain lock` / долгое ожидание | идёт другая транзакция (кассир оформляет заказ); повторить в тихое время |
| `violates check constraint … name_check` | в `menu_items` категория, которую нельзя перенести (пустая или длиннее 50 после обрезки пробелов); этого не должно быть — старое ограничение `menu_items_category_check` её не допускает; сообщите текст ошибки |
| Любая другая | не запускайте повторно «на авось»: сохраните текст ошибки, проверьте предпроверкой |

**Проверка после показала `FAIL`.**
- Строка 36, 40, 41 или 42 — после 16 повторно запускали 09 или 14. Выполните по порядку: 15, затем 16 (подтверждено локально: после этого `FAIL` нет).
- Права (строки 12–35) — не исправляйте вручную наугад: повторный запуск 16 восстанавливает определения и права; если `FAIL` остался — остановитесь и разберитесь до открытия работы персоналу.

**Нужен откат после успешной миграции.** Автоматического отката нет, и он потеряет данные (ниже). Делайте его только после резервной копии и осознанно.
Ручной откат (приложение при этом продолжает работать как «до 16»):
```sql
begin;
drop trigger if exists menu_items_category_ref on public.menu_items;
alter table public.menu_items drop constraint if exists menu_items_category_fkey;
drop function if exists public.menu_items_category_ref();
drop function if exists public.admin_add_category(text);
drop function if exists public.admin_delete_category(text);
-- перед следующей строкой сохраните:  select * from public.menu_categories;
drop table if exists public.menu_categories;
commit;
-- затем верните прежний admin_rename_category и отчёт: выполнить sql/14_reports_categories.sql, потом sql/15_menu_item_archive.sql
```

**Что нельзя откатить автоматически:**
1. **Приведение написания категорий** (регистр, пробелы) — вернуть можно только вручную из CSV `id, name, category`, сохранённого в п. 1.3.
2. **Всё, что сделали после миграции:** добавленные, переименованные, объединённые и удалённые категории; блюда, перенесённые между категориями; пустые категории справочника (при `drop table` они исчезнут).
   Переименования и объединения обратно не разворачиваются — только вручную по резервной копии.
3. **Заказы, смены и история** миграция 16 не меняет (в ней нет обращений к `orders` и `order_items`), откатывать там нечего.
4. Если после миграции вернуть 14 без 15, отчёт потеряет снимок категории удалённых блюд — поэтому всегда 14, затем 15.

## 7. Что подтверждено локально и что нет

**Подтверждено** (локальный изолированный кластер, 2026-11-15): миграция на «грязных» данных (регистр, пробелы, архивное блюдо в варианте написания) — NOTICE совпадает с предпроверкой, хеши блюд и заказов не изменились;
повторный запуск без изменений; предпроверка и послепроверка выполняются в режиме `READ ONLY`; послепроверка ловит 10 намеренных поломок (права, RLS, `search_path`, `SECURITY DEFINER`, внешний ключ, триггер);

(мне неизвестно: к Production я не подключался).
