# Разработка

## Окружение

- Python 3.12 (Tkinter входит в стандартную поставку python.org).
- Зависимости: `requirements.txt` (`supabase>=2.33,<3`).

```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp config.example.ini config.ini
```

`config.ini` — только URL проекта и **публичный** ключ. Файл в `.gitignore`; секретные ключи
приложение отклоняет. Для разовых административных действий (`reset_cashier_password.py`)
секретный ключ вводится при запуске и нигде не сохраняется.

Тесты не подключаются к Supabase: используются заглушки `Database` и источников заказов;
проверки миграций — статический разбор SQL (сам SQL локально не выполняется).

Особенности:

- `tests` — не пакет; запускать через `discover -s tests` (модули импортируют `_tk` из папки тестов).
- Все UI-тесты используют одно окно Tk (`tests/_tk.py`): второй `tk.Tk()` на macOS вешает процесс.
- Звук в тестах подменяется (`ui_kitchen.play_alert`).

Миграции 11–14 и проверки `sql/tests/11…14_*_checks.sql` выполнены 2026-11-11 на локальном PostgreSQL 17
(пакет EDB, локаль `en_US.UTF-8`, эмуляция Supabase: роли, `auth.uid()`, `auth.users`/`auth.identities`,
`extensions.pgcrypto`) вместе с 01–10 на базе с уже существующими заказами; на Supabase — **нет**.

SQL-проверки `sql/tests/*_checks.sql` выполняются в Supabase SQL Editor на **тестовом** проекте;
каждая работает в транзакции с `rollback` и ничего не сохраняет. Порядок — в [DATABASE.md](DATABASE.md).
Их можно прогнать и на локальном PostgreSQL с минимальной эмуляцией Supabase (схема `auth`,
`auth.uid()` из `request.jwt.claims`, роли `anon`/`authenticated`, права по умолчанию) — так сделано
2026-10-28, результаты и ограничения — в [MIGRATION_TEST_PLAN.md](MIGRATION_TEST_PLAN.md), раздел 15.
Локальная база должна быть с локалью UTF-8: с `C` проверка 07 падает на регистре кириллицы.

## Правила

- Изменения данных — только через RPC с проверкой `auth.uid()` и активной роли; не выдавать
  клиентам права на таблицы и не ослаблять RLS ради интерфейса.
- Новые функции: `SECURITY DEFINER` только при необходимости, всегда `set search_path = ''`,
  `revoke all … from public, anon`, `grant execute … to authenticated` — только нужным ролям.
- Миграции — новыми файлами с следующим номером; логику применённых миграций не переписывать
  (допустимы только предусловия, которые останавливают запуск, и восстановление прежних определений).
  Каждая миграция — одна явная транзакция, предусловия проверяются до изменений.
- Исключение: функцию из секции «Восстановление определений» в `08_bar_stations.sql` можно исправить,
  только если новая миграция содержит **тот же текст** этой функции — иначе повторный запуск 08
  вернул бы ошибку. Так исправлен `kitchen_menu` (08 и 09: только позиции кухни); совпадение
  проверяет `tests/test_station_menu_migration.py`. Функции 08, которые новая миграция меняет иначе
  (`admin_add_menu_item`, `admin_update_menu_item` в 09), в 08 не трогаются: после повторного
  запуска 08 нужно снова запустить новую миграцию (порядок — в [DATABASE.md](DATABASE.md#повторный-запуск)).
- Повторный запуск безопасен, только пока нет более новых миграций. Новая миграция, которая
  перезаписывает функцию или ограничение из старой, добавляет свой признак в предусловия
  старых файлов и в модель `tests/test_migration_guards.py`. Таблица — в [DATABASE.md](DATABASE.md#повторный-запуск).
- Сетевые запросы — только в фоновом потоке через `_run`; виджеты — только в главном потоке.
- Текст ошибки сервера или исключения сотруднику не показывается: известные коды — `db.RPC_ERRORS`,
  прочие — `db.PG_ERRORS` или «… Код ошибки: …»; подробности пишутся в журнал (`logging`).
  Новый код ошибки в SQL-функции — сразу текст в `RPC_ERRORS`.
- Новая функция сервера вызывается так, чтобы приложение работало и до её миграции
  (`PGRST202` — прежний путь или понятное сообщение), как `load_station_menu` для 09.
- Не коммитить `config.ini`, `.env`, `.mcp.json`, ключи и выгрузки реальных данных.

## Работа с базой

- Миграции не применяются автоматически — только вручную, сначала на тестовом проекте.
- На production — только чтение, пока владелец отдельно не подтвердил применение миграции.
- Supabase MCP (`.mcp.json`, локальный файл) настроен с `read_only=true`; подключается
  через `/mcp` в интерактивной сессии Claude Code. Даже в режиме чтения не запрашивать строки
  таблиц с персональными данными и заказами без необходимости — достаточно схемы и метаданных.
