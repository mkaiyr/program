# Кафе Бистро — что умеет приложение (обзор на 2026-10-28)

Документ описывает **текущее состояние** рабочей копии репозитория, включая ещё не закоммиченные
изменения (миграции с защитой от повторного запуска, исправления выхода из аккаунта и обработки
ответов сервера). Составлен по исходному коду, SQL-файлам, тестам и документации; приложение к
настоящему Supabase при подготовке не подключалось. Обновлено 2026-10-28: интерфейс миграции 09
(меню станций, решения администратора), тексты ошибок, неактивный сотрудник, защита от двойного
заказа; миграции 01–09 выполнены на локальном PostgreSQL с эмуляцией Supabase.

Обозначения в таблицах:

- ✅ — реализовано и проверено автоматическими тестами (на заглушках или статическим разбором SQL);
- 🟡 — реализовано в коде, но поведение на настоящем Supabase (SQL, RLS, Auth) ещё не проверено
  запуском, либо реализовано частично;
- ❌ — отсутствует.

> **Важно о проверках.** Все автоматические тесты работают без подключения к Supabase: клиент базы
> заменён заглушками, а SQL проверяется разбором текста и моделью схемы. Миграции 01–09 и

> **не** Supabase: вход через Auth, PostgREST и поведение SQL Editor проверяются только на сервере.

## Кратко простыми словами

«Кафе Бистро» — настольная программа для небольшого кафе. Кассир набирает заказ из меню (плитками
или по числовому коду блюда), программа сама считает сумму, а сервер ещё раз проверяет цены и
сохраняет заказ. Заказ сразу появляется на экранах кухни и бара — каждая станция видит только свои
позиции, без цен. Повар и бармен отмечают «Начать готовить» и «Готово» для своей части; заказ
становится «Готов», только когда готовы все станции. После этого кассир отмечает заказ «Выдан».
Администратор, кроме работы на кассе, ведёт меню: добавляет блюда, меняет цены, категории и
станцию приготовления, снимает блюда с продажи; может явно отметить заказ готовым целиком. Повар
может отмечать, каких блюд нет в наличии.

Данные хранятся в Supabase (PostgreSQL). Программа подключается с публичным ключом; всё, что
меняет данные, выполняют серверные функции, которые сами проверяют роль сотрудника.

Технологии: Python 3.12, Tkinter/ttk, `supabase-py` 2.33 (`requirements.txt`: `supabase>=2.33,<3`).

## Роли и права

Права окончательно проверяет сервер (функции `SECURITY DEFINER` и RLS); скрытые кнопки в
интерфейсе — только удобство. Колонка «Сервер» — по тексту миграций 01–08 (🟡: не проверено
запуском).

| Действие | Кассир `cashier` | Администратор `admin` | Кухня `kitchen` | Бар `bar` | Где проверяется |
|---|---|---|---|---|---|
| Вход по коду и паролю | да | да | да | да | `employee_login_email`, Supabase Auth, `profiles` |
| Экран после входа | касса | касса + «Управление меню» | экран кухни (2 вкладки) | экран бара | `main.App.show_main` ✅ |
| Видит меню с ценами | только доступные позиции | все позиции | нет | нет | RLS `menu_select_staff`, `menu_select_admin` 🟡 |
| Оформляет заказ | да | да | нет | нет | `create_order` → `is_active_staff()` 🟡 |
| Видит заказы с суммами | только свои | все | нет | нет | RLS `orders_select_own`, `orders_select_admin` 🟡 |
| Видит заказы станции (без цен) | нет | функции доступны, но в интерфейсе админа экрана станций нет | кухонные позиции | барные позиции | `kitchen_orders`, `bar_orders` 🟡 |
| «Начать готовить» / «Готово» для части заказа | нет | любая станция (только через RPC, кнопки в интерфейсе нет) | только кухня | только бар | `set_station_status` 🟡 |
| «Выдан» (ready → completed) | свои заказы | любые | нет | нет | `set_order_status` 🟡 |
| «Готов принудительно» (все станции) | нет | да, с подтверждением | нет | нет | `admin_force_order_ready` 🟡 |
| Добавить / изменить позицию меню | нет | да | нет | нет | `admin_add_menu_item`, `admin_update_menu_item` 🟡 |

(✅ тесты `test_status_access`, `test_bar_stations`), и серверные функции проверяют активность.

## 1. Назначение приложения

- Касса небольшого кафе: каталог блюд, корзина, оформление заказа с расчётом суммы на сервере.
- Передача заказа на кухню и в бар: каждая станция получает только свои позиции.
- Отслеживание статуса: «Принят» → «Готовится» → «Готов» → «Выдан».
- Ведение меню: коды позиций, цены, категории, станция приготовления, наличие.
- Рассчитано на несколько рабочих мест (касса, кухня, бар), которые работают с одной базой
  Supabase. Цены в тенге (₸).

|---|---|---|
| Каталог плитками | ✅ | Код · название · цена; нажатие добавляет 1 шт. Рисуется не больше 60 плиток (подсказка уточнить поиск). |
| Категории | ✅ | Кнопки-«чипы» «Все» + категории из меню. |
| Поиск | ✅ | Поле «Код или название»: цифры — код целиком или по началу (и цифры в названии), иначе подстрока названия, без учёта регистра; точный код — первым. |
| Добавление по коду | ✅ | Enter в поиске: точный код или единственное найденное блюдо → в заказ. Пока идёт запрос, Enter ничего не меняет. |
| Корзина | ✅ | Таблица «Позиция / Цена / Кол-во / Сумма», кнопки «−», «+», «Удалить», «Очистить» (с подтверждением). 0 шт. — строка удаляется. |
| Ограничения | ✅ | Не больше 100 шт. одной позиции и 50 разных позиций (совпадает с серверной проверкой). |
| Сумма | ✅ | Считается локально (`Decimal`, без ошибок округления) и **заново на сервере**; в подтверждении показывается серверная сумма. |
| Оформление заказа | ✅ / 🟡 | «Оформить заказ» → RPC `create_order`. Пустой заказ не отправляется; повторное нажатие во время запроса игнорируется; корзина заблокирована, пока идёт запрос. |
| Защита от дублей | ✅ / 🟡 | Один `client_request_id` на неизменённый заказ: повтор после обрыва связи не создаёт второй заказ (сервер вернёт «повторный запрос — заказ был сохранён ранее»); изменённая корзина — новый ID. | Изменилось меню | ✅ / 🟡 | Сервер отклоняет заказ, если позиция снята с продажи или цена изменилась (`MENU_CHANGED`); касса перезагружает меню, убирает снятые позиции, обновляет цены и сообщает, что изменилось. |
| «Обновить меню», «Заказы», «Выйти» | ✅ | «Выйти» спрашивает подтверждение, если заказ не оформлен; недоступна во время запроса. |

## 6. Бар (экран «Бар»)

Тот же экран станции для роли `bar` (`BarFrame`): вкладка «Заказы» — барные позиции без цен
(`bar_orders`), «Начать готовить» / «Готово» для барной части; вкладка «Меню» — как у кухни, но
только позиции бара (`station_menu`, `station_set_menu_item_available`, миграция 09). До миграции 09
во вкладке сообщение «появится после обновления базы»; `kitchen_menu` бар не вызывает. Сервер: бар
не оформляет продажи, не читает таблицы меню и заказов, меняет статус только станции `bar`
(проверено на локальном PostgreSQL). ✅ (клиент) / 🟡 (Supabase).

Готовый напиток не делает готовым смешанный заказ «еда + напиток»: заказ «Готов», только когда
готовы все его станции (✅ модель и тексты SQL; 🟡 сервер).

## 8. База данных

Таблицы (по `sql/01_schema.sql` … `08_bar_stations.sql` и `docs/DATABASE.md`):

| Таблица | Назначение | Основные поля и ограничения |
|---|---|---|
| `profiles` | сотрудник (1:1 с `auth.users`) | `full_name` 1–100, `role` ∈ cashier/admin/kitchen/bar, `is_active`, `employee_code` 4–6 цифр, уникален |
| `menu_items` | позиции меню | `code` (постоянный, уникальный, 1…99999999), `name` (уникально), `category`, `price` > 0, `is_available`, `station` ∈ kitchen/bar |
| `orders` | заказ | `cashier_id` → `profiles`, `client_request_id` (уникален, защита от дублей), `total` > 0, `status` ∈ accepted/preparing/ready/completed, `created_at` |
| `order_items` | позиции заказа | `order_id` → `orders` (каскадно), `menu_item_id` → `menu_items` (удаление запрещено), снимки `item_name`, `unit_price`, `item_code`, `station`; `quantity` 1–100; `line_total` вычисляется; позиция не повторяется в заказе |
| `order_stations` | часть заказа на станции | PK (`order_id`, `station`), `status` ∈ accepted/preparing/ready; клиентам закрыта полностью |

Серверные функции (все клиентские — `SECURITY DEFINER`, `search_path = ''`, `EXECUTE` отозван у
`PUBLIC` и `anon`, кроме `employee_login_email`):

| Функция | Что делает |
|---|---|

## 13. Известные проблемы

Только подтверждённые кодом, тестами или метаданными:

1. **Миграции на рабочем сервере применялись вручную**; история миграций Supabase пуста, тексты
   функций на сервере не сверены с файлами (MCP, 2026-10-24).
2. **Старые версии SQL-файлов в истории Git** (коммит `e819f75` и раньше) не имеют защиты от
   повторного запуска: запуск 01, 02, 04, 05, 06 поверх 08 вернул бы старую логику, а 05 удалила
   бы роль `bar`.
3. **Статусы заказов, изменённые старой логикой** (если старые 04/05 когда-то запускались после 08),
   повторная 08 не исправляет.
4. **`employee_login_email` доступна без входа (`anon`)**: перебором кодов можно узнать email
   активных сотрудников (известное ограничение из `03_employee_code.sql`; советник Supabase — WARN).
   Рекомендовано использовать служебные email.
5. **Защита от утёкших паролей в Supabase Auth выключена** (советник Supabase, 2026-10-24).
6. **Выход использует внутренние методы `supabase-py` 2.33** (`_remove_session`,
   `_notify_all_subscribers`): публичного локального выхода в библиотеке нет; при обновлении
   библиотеки поломку покажут тесты.
7. **Гонка в библиотеке**: если таймер обновления токена уже выполняет обновление в момент выхода,
   он может снова сохранить старую сессию (не воспроизводилось, по коду библиотеки).
8. **Отзыв истёкшего токена в фоне не обновляет его**: при выходе после долгого отсутствия связи
   серверная сессия доживёт до своего срока (локально её уже нет).
9. **Вход после выхода может ждать до 15 с**, пока не завершится отзыв прежней сессии на
   недоступном сервере (обычно — не дольше HTTP-таймаута 5 с).
10. **Проверка адреса в `config.py` мягкая**: например, `https://abc.supabase.com` проходит, и
    ошибка проявится только как «Нет связи» при входе.
11. ~~`reset_cashier_password.py` с заглушкой `user_id`~~ — исправлено 2026-10-28: UUID
    спрашивается при запуске и проверяется.
12. **Уникальность названий без учёта регистра** работает только в базе с локалью UTF-8 (локально:

## Сценарии работы

### Вход кассира и создание заказа

1. Кассир вводит код сотрудника (4–6 цифр) на цифровой клавиатуре и пароль, нажимает «Войти».
2. Программа находит email по коду (`employee_login_email`), Supabase Auth проверяет пароль,
   программа читает профиль; активный кассир попадает на экран «Касса», меню загружается.
3. Кассир выбирает категорию или вводит код/название; нажимает плитки или вводит код и Enter.
4. В «Текущем заказе» меняет количество «−»/«+», удаляет лишнее; «Итого» пересчитывается сразу.
5. «Оформить заказ» → сервер проверяет наличие и цены, считает сумму, сохраняет заказ, позиции и
   части по станциям. Кассир видит «Заказ № N оформлен. Сумма: …», корзина очищается.
6. Если позиция снята с продажи или цена изменилась — сообщение «Меню изменилось», меню и корзина
   обновляются; кассир проверяет заказ и оформляет снова.

### Приготовление на кухне и в баре

1. Экраны кухни и бара обновляются каждые 7 с; новый заказ появляется со звуковым сигналом и
   надписью «Новый заказ № N».
2. Повар видит только блюда кухни, бармен — только напитки бара, без цен.
3. Каждый нажимает «Начать готовить» → его часть «Готовится», общий статус заказа — «Готовится».
4. «Готово» → его часть «Готов» и исчезает с экрана станции. Пока другая станция не готова, общий
   статус остаётся «Готовится».
5. Повар может на вкладке «Меню» отметить «Нет в наличии» — касса перестанет принимать это блюдо
   (после «Обновить меню» или отказа сервера при оформлении).

### Завершение и выдача

1. Когда готовы все станции заказа, сервер ставит общий статус «Готов».
2. Кассир открывает «Заказы» (или нажимает «Обновить»), выбирает заказ «Готов» и нажимает
   «Отметить «Выдан»» с подтверждением; кассир — только свои заказы, администратор — любые.
3. Если блюдо готово, но станцию забыли отметить, администратор может нажать «Готов принудительно»
   (с предупреждением, что все станции будут отмечены «Готов»).

### Вход администратора и изменение меню

1. Администратор входит своим кодом — открывается касса с кнопкой «Управление меню».
2. В модальном окне находит позицию поиском, выбирает её — данные появляются в форме.
3. Меняет название, категорию, цену или станцию («Кухня»/«Бар»), «Сохранить изменения»; код
   остаётся постоянным.
4. «Новая позиция»: заполняет поля, код можно оставить пустым — сервер назначит следующий; «Добавить».
5. «Снять с продажи (Нет)» с подтверждением — кассиры перестают видеть позицию.
6. После закрытия окна касса перезагружает меню.

### Потеря соединения, ошибка сервера и безопасный выход

1. Нет связи при оформлении — «Заказ не подтверждён — нажмите «Оформить» ещё раз»; повтор с тем же
   ID не создаст дубль, даже если первый запрос дошёл до сервера.
2. Нет связи на кухне — строка статуса «… Повторим автоматически через 7 с», работа продолжается
   после восстановления.
3. Ошибка сервера — понятное сообщение; экран остаётся рабочим, кнопки снова активны.
4. Сессия истекла — сообщение «Сессия истекла. Войдите снова.» и экран входа; ответы, пришедшие
   позже, игнорируются.
5. «Выйти» — экран входа появляется сразу, токен на этом компьютере удалён; сервер получает отзыв
   сессии в фоне, если доступен. Следующий сотрудник входит со своей сессией.

## Архитектура

```
Tkinter (main.py) ──► db.Database ──► supabase-py ──► Supabase
  экраны ui_*.py        AppError         PostgREST (таблицы под RLS, RPC SECURITY DEFINER)
  фоновые потоки                         Auth (email + пароль)
```

| Модуль | Назначение |
|---|---|
| `main.py` | окно `App`, экран входа, выбор экрана по роли, выход |
| `config.py` | чтение `config.ini`, запрет секретных ключей |
| `db.py` | все обращения к Supabase, проверка ввода и ответов, тексты ошибок, статусы и переходы |
| `search.py` | общий поиск по коду и названию |
| `ui_theme.py` | цвета, шрифты, стили, карточки, прокручиваемая область |
| `ui_login.py` | вход по коду и паролю, экранная клавиатура |
| `ui_order.py` | касса |
| `ui_orders.py` | окно «Заказы» |
| `ui_deleted_orders.py` | окно «Удалённые заказы» и журнал окончательных удалений |
| `ui_admin.py` | «Управление меню» |
| `ui_kitchen.py` | экраны кухни и бара, автообновление, звук |
| `ui_kitchen_menu.py` | вкладка «Меню» кухни |
| `reset_cashier_password.py` | разовый служебный скрипт смены пароля (требует правки, см. раздел 13) |
| `sql/` | миграции 01–08, `seed/demo_menu.sql`, `tests/*_checks.sql` |

Подробнее: `docs/ARCHITECTURE.md`, `docs/DATABASE.md`, `docs/DEVELOPMENT.md`,
`docs/MIGRATION_TEST_PLAN.md`.
