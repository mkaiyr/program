# План испытания миграций 01–08 на тестовом проекте Supabase

> **Статус плана.** Документ подготовлен по исходникам `sql/` без запуска SQL. Ни одна миграция,
> SQL-проверка или запрос из этого плана на PostgreSQL ещё не выполнялись. Ожидаемые результаты —
> это то, что следует из текста файлов; каждый шаг подтверждается только фактическим запуском.
>
> **Рабочий проект Supabase в этом плане не используется ни на одном шаге.** Если на любом шаге
> есть сомнение, что открыт тестовый проект, — остановиться (раздел 11).

## 1. Цель и границы

Проверить на новом изолированном проекте:

1. установку `sql/01_schema.sql` … `sql/08_bar_stations.sql` на пустую базу;
2. тестовое меню `sql/seed/demo_menu.sql` и его отказ на непустом меню;
3. SQL-проверки `sql/tests/07_menu_codes_checks.sql` и `sql/tests/08_bar_stations_checks.sql`;
4. остановку текущих версий 01, 02, 04, 05, 06 (и 07) поверх схемы 08 без изменений схемы и данных;
5. повторный запуск 08: те же функции и сигнатуры до и после.

Вне плана: приложение (`main.py`, `config.ini`), рабочая база, `sql/tests/05_kitchen_checks.sql` и
`sql/tests/06_kitchen_menu_checks.sql` (см. раздел 12, вопросы В3–В4).

## 2. Предварительные условия: проект точно тестовый

1. **Создать новый проект** Supabase с явным именем, например `cashier-migration-test`.
   Не использовать рабочий проект, его ветки (branching) или копию рабочей базы.
   Не переносить реальные данные: пользователей, профили, меню, заказы.
2. **Проверка адреса без секретов.** В Dashboard → Project Settings → General сверить:
   - имя проекта — тестовое;
   - Reference ID тестового проекта **не совпадает** с Reference ID рабочего проекта
     (рабочий — смотреть в Dashboard рабочего проекта; значение в этот документ не записывать);
   - в адресной строке браузера на странице SQL Editor (`…/dashboard/project/<ref>/sql/…`) тот же
     `<ref>`, что у тестового проекта.

   Ключи API, пароль базы и строку подключения не копировать и не вставлять в заметки.
   `config.ini` не открывать и не менять: приложение в плане не участвует.
3. **Проверка пустой схемы (до шага 01).** В SQL Editor тестового проекта выполнить запрос только
   на чтение; ожидаемый результат `0, true, 0`:
   ```sql
   select (select count(*) from pg_tables where schemaname = 'public') as public_tables,
          to_regclass('public.orders') is null as no_orders,
          (select count(*) from auth.users) as auth_users,
          (select count(*) from pg_proc where pronamespace = 'public'::regnamespace) as public_functions;
   ```
   Первые три значения — любое другое значение означает, что это не новый проект: **остановиться**.
   `public_functions` ожидается 0; если нет — записать: эти функции войдут во все снимки.
4. **Повторная проверка перед каждым шагом.** Название проекта в шапке Dashboard и `<ref>` в адресе
   сверять перед каждым запуском файла. Начиная с шага 2 (пользователи) дополнительный признак —
   в `auth.users` только тестовые адреса (см. 6.1):
   ```sql
   select count(*) filter (where email not like '%@migration-test.invalid') as foreign_users,
          count(*) as all_users
     from auth.users;
   ```
   Ожидается `foreign_users = 0`.
5. Журнал результатов (раздел 10) заполняется по ходу; копируется текст последней строки
   результата или сообщения об ошибке.

## 3. Транзакции, `RAISE` и SQL Editor

Факты из файлов:

- каждый файл 01–08 и `seed/demo_menu.sql` начинается с `begin;` и заканчивается `commit;`
  (проверено разбором текста; парсер PostgreSQL 17 синтаксических ошибок не нашёл);
- SQL-проверки `sql/tests/*_checks.sql` начинаются с `begin;` и заканчиваются `rollback;`;
- предусловия — `DO`-блоки с `RAISE EXCEPTION 'ОСТАНОВЛЕНО: …'` сразу после `begin;`.

Что известно о PostgreSQL в целом (по документации, не по запуску этих файлов):

- ошибка в `DO`-блоке прерывает эту команду; внутри открытой транзакции транзакция переходит в
  состояние ошибки, последующие команды до `ROLLBACK` отвергаются, `COMMIT` такой транзакции
  выполняет откат — изменения прерванной транзакции не сохраняются;
- `DO`-блок с разделом `EXCEPTION` работает как вложенная транзакция: если ошибка перехвачена,
  всё, что блок успел изменить, откатывается, а внешняя транзакция продолжается. SQL-проверки
  используют это намеренно: например, попытка бармена оформить продажу
  (`08_bar_stations_checks.sql`, блок с `'FAIL: бармен оформил продажу'`) откатывается своим
  блоком. Заказы, на которые опираются следующие шаги (смешанный, «только еда», «только напиток»,
  заказ принудительной готовности), создаются в блоках **без** `EXCEPTION` и остаются до
  финального `rollback;`;
- `set_config(…, true)` и `set local role …` действуют только до конца текущей транзакции.
  SQL-проверки передают id тестовых пользователей и заказов между командами через
  `set_config('test.…', …, true)` — поэтому они **работают только если весь файл выполняется
  одной транзакцией в одном сеансе**.

**Не известно без реального теста:** как SQL Editor Supabase отправляет многооператорный скрипт
(одним запросом или по командам, в одном сеансе или нет), прекращает ли выполнение после первой
ошибки, показывает ли все ошибки или только первую, закрывает ли сеанс с прерванной транзакцией и
связаны ли разные вкладки с одним сеансом. От этого зависит главное:

- если редактор выполняет скрипт одной транзакцией и останавливается на первой ошибке —
  предусловия миграций останавливают весь файл, как задумано;
- если редактор выполняет команды по отдельности и продолжает после ошибки, предусловие
  остановит только свою команду, а **следующие команды миграции выполнятся**. Именно это и
  проверяют защитные тесты раздела 9 — снимком «после», а не текстом ошибки. Поэтому они только
  в тестовом проекте и только после успешных шагов 1–4.

После **каждого** запуска, завершившегося ошибкой или `ОСТАНОВЛЕНО`:

1. записать текст ошибки дословно (включая строки `CONTEXT`, если редактор их показывает) и то,
   продолжил ли редактор выполнять команды после неё;
2. в **той же** вкладке выполнить `rollback;` (без транзакции PostgreSQL выдаст предупреждение
   `there is no transaction in progress` — это допустимо). Связаны ли вкладки с одним сеансом,
   не известно, поэтому `rollback;` в другой вкладке ничего не гарантирует;
3. проверить, что не осталось незавершённых транзакций (раздел 4, запрос «Незавершённые
   транзакции»): открытая прерванная транзакция держит блокировки, и следующий шаг с `ALTER TABLE`
   (например, повторная 08) будет ждать бесконечно;
4. снять снимок (раздел 4) и сравнить с предыдущим;
5. отметить в журнале фактическое поведение редактора — это и есть результат проверки.

Если любой шаг выполняется дольше минуты — не запускать ничего нового, проверить незавершённые
транзакции.

## 4. Снимок схемы и данных (только чтение)

Используется до и после каждого защитного теста и повторного запуска 08. Запрос только читает
каталоги и тестовые таблицы; он ещё не выполнялся — если он сам упадёт, это фиксируется в журнале,
а план останавливается до исправления запроса (не миграций). Применим после шага 08 (нужна
`order_stations`).

```sql
-- Снимок public: по строке на часть, сравнивать n и fingerprint до и после
-- pg_get_functiondef включает тело, SECURITY DEFINER и SET search_path; права и владелец — отдельно
select 'functions' as part, count(*) as n,
       md5(string_agg(p.oid::regprocedure::text || ':' || md5(pg_get_functiondef(p.oid))
                      || ':' || coalesce(p.proacl::text, '') || ':' || pg_get_userbyid(p.proowner)::text,
                      ',' order by p.oid::regprocedure::text)) as fingerprint
  from pg_proc p where p.pronamespace = 'public'::regnamespace
union all
select 'columns', count(*),
       md5(string_agg(table_name || '.' || column_name || ':' || data_type || ':' || is_nullable
                      || ':' || coalesce(column_default, ''), ',' order by table_name, ordinal_position))
  from information_schema.columns where table_schema = 'public'
union all
select 'constraints', count(*),
       md5(string_agg(conrelid::regclass::text || '.' || conname || ':' || pg_get_constraintdef(oid), ','
                      order by conrelid::regclass::text, conname))
  from pg_constraint where connamespace = 'public'::regnamespace
union all
select 'triggers', count(*),
       md5(string_agg(tgrelid::regclass::text || '.' || tgname || ':' || tgenabled::text || ':' || tgfoid::regproc::text,
                      ',' order by tgrelid::regclass::text, tgname))
  from pg_trigger
 where not tgisinternal and tgrelid in (select oid from pg_class where relnamespace = 'public'::regnamespace)
union all
select 'policies', count(*),
       md5(string_agg(tablename || '.' || policyname || ':' || permissive || ':' || roles::text || ':' || cmd
                      || ':' || coalesce(qual, '') || ':' || coalesce(with_check, ''),
                      ',' order by tablename, policyname))
  from pg_policies where schemaname = 'public'
union all
select 'relations', count(*),
       md5(string_agg(c.relname || ':' || c.relkind::text || ':' || coalesce(c.relacl::text, '')
                      || ':' || c.relrowsecurity::text || ':' || c.relforcerowsecurity::text
                      || ':' || pg_get_userbyid(c.relowner)::text, ',' order by c.relname))
  from pg_class c where c.relnamespace = 'public'::regnamespace
union all
select 'menu_items', count(*), md5(coalesce(string_agg(t::text, ',' order by t.id), '')) from public.menu_items t
union all
select 'profiles', count(*), md5(coalesce(string_agg(t::text, ',' order by t.id), '')) from public.profiles t
union all
select 'orders', count(*), md5(coalesce(string_agg(t::text, ',' order by t.id), '')) from public.orders t
union all
select 'order_items', count(*), md5(coalesce(string_agg(t::text, ',' order by t.id), '')) from public.order_items t
union all
select 'order_stations', count(*), md5(coalesce(string_agg(t::text, ',' order by t.order_id, t.station), ''))
  from public.order_stations t
union all
select 'menu_item_code_seq', 1, md5(last_value::text || ':' || is_called::text) from public.menu_item_code_seq;
```

Что снимок **не** охватывает: значения identity-последовательностей `menu_items`, `orders`,
`order_items` (они законно растут при откаченных вставках), индексы — только по имени и виду
(через `relations`), комментарии, схемы кроме `public` (в том числе `auth`).

Какие строки могут законно измениться:

| Между чем сравнивается | Может измениться | Не должно меняться |
|---|---|---|
| До и после SQL-проверок 07/08 (раздел 8) | `menu_item_code_seq` (номера, выданные в откаченной транзакции, не возвращаются) | все остальные строки |
| До и после защитных тестов, повторного seed (разделы 7, 9) | ничего | все строки |
| До и после повторной 08 (9.1) | `order_stations` — только если есть заказы без частей по станциям (на тестовом проекте после раздела 8 заказов нет, поэтому не ожидается) | все остальные строки |

Незавершённые транзакции (только чтение; ожидается 0 строк). Видны ли сеансы SQL Editor роли,
от которой выполняется запрос, — не проверено; пустой результат записать вместе с этой оговоркой:

```sql
select pid, state, xact_start, left(query, 80) as last_query
  from pg_stat_activity
 where datname = current_database() and pid <> pg_backend_pid()
   and state in ('idle in transaction', 'idle in transaction (aborted)');
```

Если строки есть — ничего не запускать дальше. Закрыть вкладки SQL Editor и повторить запрос; если
сеанс не исчез, на **тестовом** проекте его можно завершить `select pg_terminate_backend(<pid>);`
(незафиксированные изменения сеанса при этом откатываются) и записать это в журнал.

## 6. Шаг 2: тестовые пользователи и профили

### 6.1. Что нужно SQL-проверкам (по тексту `sql/tests/*`)

- `07_menu_codes_checks.sql`: активный `admin` и активный `cashier` в `public.profiles`

### 6.2. Порядок

1. Dashboard → Authentication → Users → Add user: два пользователя с адресами только в
   зарезервированном домене, например `admin@migration-test.invalid` и
   `cashier@migration-test.invalid`, пароли — одноразовые тестовые, не используемые нигде больше.

   - кассир — шаблон «Профиль кассира» в конце `sql/01_schema.sql`;
   - администратор — шаблон «Назначение администратора» в конце `sql/02_admin_menu.sql`
     (вариант `insert`, так как профиля ещё нет);
   - код сотрудника кассиру — шаблон «Назначение кодов» в конце `sql/03_employee_code.sql`
     (4–6 цифр, уникальный; например `1002`).
   Повар и бармен для проверок не обязательны (шаблоны — в концах `05_kitchen_status.sql` и
   `08_bar_stations.sql`).

Ограничения, которым должны соответствовать профили (из `01_schema.sql`, `03_employee_code.sql`,

- `profiles.id` ссылается на `auth.users(id)` — поэтому сначала пользователь в Authentication,

- `full_name` — от 1 до 100 символов после `trim`;
- `role` — одно из `cashier`, `admin`, `kitchen`, `bar` (`profiles_role_check` после 08);
- `employee_code` — `NULL` или 4–6 цифр (`profiles_employee_code_format`), уникален

  ровно по одному, чтобы было однозначно, кто участвует;
- проверка 08 читает `employee_code` именно у этого кассира (`test.cashier_id`); код
  администратора проверками не используется.

## 7. Шаг 3: тестовое меню

1. Убедиться, что меню пустое: `select count(*) from public.menu_items;` = 0.
2. Запустить `sql/seed/demo_menu.sql` целиком.
3. Ожидается: без ошибок; `select code, name, category, price, is_available, station from public.menu_items order by code;`
   — 5 строк, коды разные и не меньше 1001, `is_available = true`, `station = 'kitchen'`.
   Точное соответствие кодов названиям из файлов не следует — только записать.
4. **Защитный тест seed.** Снимок (раздел 4) → запустить `sql/seed/demo_menu.sql` ещё раз →
   ожидается `ОСТАНОВЛЕНО: в меню уже есть позиции, тестовое меню добавляется только в пустую базу`
   → `rollback;` в той же вкладке → незавершённых транзакций нет → снимок. **Все** строки снимка
   совпадают; в частности `menu_items` — те же 5 строк. Если появились ещё 5 позиций, редактор
   выполнил `insert` после ошибки предусловия — это результат проверки поведения редактора:
   остановиться (раздел 11).
5. Ручной шаг из конца 08 (напитки на станцию `bar`) **не выполнять до SQL-проверок**: проверка 08
   сама назначает станции двум позициям и откатывает это; выполнение перед ней допустимо, но
   меняет исходные данные без необходимости. Если нужен — после шага 5.

## 9. Шаг 5: защитные тесты поверх схемы 08

  `set local role authenticated`. Читает ли `auth.uid()` в тестовом проекте именно этот параметр и
  разрешено ли роли SQL Editor переключаться на `authenticated` и `anon` — из файлов не следует.
  Проверяется шагами 4.1–4.2.
- **В2.** Сохранятся ли тестовые данные проверок при ошибке посреди проверки зависит от поведения
  редактора (раздел 3); после любой ошибки — `rollback;` и контроль из раздела 8.
- **В3.** `sql/tests/06_kitchen_menu_checks.sql` написана для состояния после 06 и не содержит
  проверки на более новую схему; применима ли она после 07/08 — не проверено, в план не входит.
- **В4.** `sql/tests/05_kitchen_checks.sql` после 08 по тексту останавливается с `ПРОПУСК`;
  в план не входит.
- **В5.** Порядок назначения кодов тестовым позициям при многострочном `insert` из файлов не следует.
- **В6.** Выполняет ли SQL Editor файл одной транзакцией в одном сеансе — от этого зависят и
  SQL-проверки (`set_config(…, true)`, `set local role`), и предусловия миграций (раздел 3).
- **В7.** Видит ли роль SQL Editor чужие сеансы в `pg_stat_activity`: пустой результат запроса
  «Незавершённые транзакции» без этого не доказывает их отсутствие.
- **В8.** Разрешение вызовов проверки 07 (`admin_add_menu_item` с 3 и 4 аргументами,
  `admin_update_menu_item` с 4) в 5-параметровые версии после 08 следует из правил PostgreSQL для
  параметров по умолчанию, но не проверялось запуском.
- **В9.** Утверждение проверки 08 о владельце функций (владелец функций = владелец `order_stations`)
  выполнится, только если все файлы запускаются от одной роли SQL Editor.
