## 3. Единый каталог (приоритет №1)

**Принцип:** единственный источник — `menu_items` в общей БД. Сайт не получает собственной таблицы блюд, а читает то же через публичное представление.

Что уже есть в `menu_items` и как соотносится с требованиями:

| Требование | Решение |
|---|---|
| постоянный ID | `menu_items.id` (+ `code`); для сайта добавляется неизменяемый `slug` |
| название, категория, цена | `menu_items.name/category/price` (редактирует администратор через существующие `admin_*`) |
| доступность | `is_available` — «временно нельзя заказать» |
| активность в меню | `archived_at is null` и подтверждено (`approved_at`) — «существует в каталоге и продаётся» |
| скрыто с сайта, но есть в кассе/истории | **новое:** `menu_item_public.published` |
| дата создания/изменения | `created_at` есть; **новое:** `updated_at` (триггер) |
| описание, вес, фото, порядок, «рекомендуем» | **новое:** расширение `menu_item_public` (1:1 с `menu_items`, не копия блюда) |
| состав и аллергены | **новое:** `ingredients`, `ingredient_allergens`, `menu_item_ingredients` (описательный состав для сайта; не путать с технологической картой) |

Набросок (не выполнялось):
```sql
create table public.menu_item_public (
  item_id bigint primary key references public.menu_items(id) on delete cascade,
  slug text not null unique check (slug ~ '^[a-z0-9]+(-[a-z0-9]+)*$'),
  description text not null default '', weight_value int, weight_unit text,
  recommended boolean not null default false, sort int not null default 0,
  photo_file text, photo_thumb text, photo_alt text,
  published boolean not null default false, updated_at timestamptz not null default now());
create table public.allergens (id text primary key, name text not null);
create table public.ingredients (id text primary key, name text not null);
create table public.ingredient_allergens (ingredient_id text references public.ingredients, allergen_id text references public.allergens,
  status text not null check (status in ('contains','may_contain')), primary key (ingredient_id, allergen_id));
create table public.menu_item_ingredients (item_id bigint references public.menu_items on delete cascade, ingredient_id text references public.ingredients,
  sort int not null default 0, primary key (item_id, ingredient_id));
```
Публичный API: `public_menu()` — `SECURITY DEFINER`, доступна роли `anon`, возвращает JSON **ровно в формате контракта сайта** (`docs/contracts/public_catalog.md`) только для `published and archived_at is null`; **без** закупочных цен, кодов станций, служебных полей. Сайт получает каталог через `catalog-source.js` (режим `api`), цены и доступность всегда от сервера; корзина хранит только id и количество.

История не переписывается: `order_items` уже хранит снимки названия, цены, категории; изменение каталога заказы не трогает (это сохраняется).

## 4. Склад (набросок модели; всё — серверные функции, клиенты не пишут в таблицы напрямую)

- `stock_products(id, name, category, unit, purchase_price, min_stock, stock, active, created_at, updated_at)`; единицы: кг, г, л, мл, шт; `check (stock >= 0)` — отрицательный остаток невозможен на уровне БД; поле `stock` меняет только функция, пишущая движение.
- `stock_movements(id, product_id, delta, kind, order_id, receipt_id, count_id, actor, note, created_at)`; виды: `receipt`, `sale`, `void`, `refund`, `count`; **журнал только на добавление** (триггеры запрещают update/delete — как у журналов удалений); остаток = сумма движений (проверяется отдельным запросом/функцией).
- `suppliers(id, name unique, contacts, comment, active)`; сумма закупок — запрос по подтверждённым поступлениям (задолженность не вводим: нужна полноценная модель расчётов).
- `stock_receipts(id, supplier_id, doc_date, comment, status draft|confirmed, total, client_request_id unique, confirmed_at, confirmed_by)` + `stock_receipt_lines(receipt_id, product_id, qty, unit, unit_price, line_total)`. Функция `receipt_confirm(id)`: блокирует документ `for update`, при статусе `confirmed` возвращает `duplicate = true` без изменений; иначе пишет движения и увеличивает остатки одной транзакцией.
- Технологические карты: `recipe_lines(menu_item_id, product_id, qty, unit)`. **Пустая карта — не списываем и показываем предупреждение.** Реальные рецептуры вносит владелец через интерфейс; в системе ничего не придумывается.
- Инвентаризация: `stock_counts` + `stock_count_lines(count_id, product_id, expected, actual, diff, reason)`; `count_confirm(id)` пишет движение «корректировка» = факт − текущий остаток, причина обязательна при расхождении, повтор не меняет.

### Продажа, отмена, возврат — атомарно и без двойного списания
Расширение `place_order` (новой миграцией, миграция 11 не меняется): после записи заказа в той же транзакции вызывается `stock_apply_sale(order_id)`:
1. рассчитывает расход по техкартам (пересчёт единиц), блюдо без карты → предупреждение в ответе, расхода нет;
2. блокирует затрагиваемые продукты `for update` **в порядке id** (нет взаимных блокировок при одновременных заказах кассы и сайта);
3. при нехватке — ошибка `INSUFFICIENT_STOCK`, **весь заказ откатывается** (политика «блокировать» — см. решения);
4. пишет движения; защита от повтора — уникальная запись `order_stock_ops(order_id, 'sale')`, а не интерфейс.
Обратный документ при `void_order`/возврате — одна запись `order_stock_ops(order_id, 'reversal')` (уникальна): возвращается ровно списанное и не возвращённое ранее, поэтому отмена + возврат не восстановят остаток дважды. Это уже проверено на эталонной модели (см. п. 6).

Кассир видит каталог и остатки (если решим) только на чтение. Роли `stockkeeper`, `manager`, `courier` потребуют изменения `profiles_role_check` — **отдельное разрешение**. Сайт (`anon`) вызывает только `public_menu()` и, позже, `web_place_order()`; `service_role` на сайте не используется.

## 8. Решения, нужные от владельца
1. **Исходный каталог:** чьи демонстрационные цены и названия считать основой (касса или сайт) и что делать с блюдами «только в кассе» (Круассан, Сэндвич) и «только на сайте» (27 блюд).
2. **Политика при нехватке продукта:** блокировать продажу (рекомендую для склада) или разрешать с предупреждением без ухода в минус.
3. **Момент списания для заказа с сайта:** при создании или при принятии сотрудником (рекомендую при принятии).
4. **Отмена/возврат:** возвращать продукты, если блюдо ещё не готовили; если готовили — списывать как потери? (сейчас модель возвращает всё один раз).
5. **Надбавка 10%:** применять и к заказам с сайта?
6. **Видимость остатков кассиру** (только чтение) и нужны ли роли `stockkeeper`/`manager` сразу.
7. **Новая локальная тестовая БД:** разрешите создать (предлагаю имя `cashier_catalog_dev`) и скажите, как запускать локальный PostgreSQL (на этой машине в PATH нет `psql`/`pg_ctl`).
