## 2. Настольное приложение

**Архитектура.** `Tkinter → db.Database → supabase-py → Supabase (PostgREST + Auth)`. Клиент использует только публичный ключ (`config.py` отклоняет `service_role`). Чтение — `select` под RLS, запись — только RPC `SECURITY DEFINER` с `search_path = ''`. Вход: код сотрудника (4–6 цифр) → `employee_login_email` → Supabase Auth (email `<uuid>@bistro.local` + пароль). Роли: `admin`, `cashier`, `kitchen`, `bar` (в таблице `profiles`). Ролей `manager`, `stockkeeper`, `courier` нет.

**Схема (миграции 01–16, не менять).** `profiles`, `menu_items` (`id`, `code`, `name`, `category`→`menu_categories`, `price`, `is_available`, `station`, `approved_at`, `archived_at`), `orders` (`id`, `cashier_id`, `client_request_id` уникален, `total`, `subtotal`, `service_percent`, `service_amount`, `status` ∈ accepted/preparing/ready/completed, `deleted_at`, `voided_at`, `void_reason`, `shift_id`), `order_items` (снимки названия, цены, станции, кода, категории; `menu_item_id` может быть NULL), `order_stations` (статус станции), `cash_shifts`, `cash_movements`, журналы `menu_item_reviews`, `order_purge_log`, `menu_item_purge_log`.

**Как создаётся заказ.** `place_order(request_id, items, expected_total)`: сервер проверяет доступность и цены, считает подытог и **надбавку 10%**, сверяет с ожидаемым итогом (`TOTAL_MISMATCH`), создаёт заказ, позиции и станции; повторная отправка защищена `client_request_id`. Выдача — `set_order_status(ready→completed)`, аннулирование — `void_order` (в выручку не входит), удаление — `delete_order` (мягкое).

**Чего в приложении нет совсем:** склад, продукты, поставщики, поступления, технологические карты, инвентаризация, печать чеков, способ оплаты в заказе, клиенты, адреса, доставка, курьеры, источник заказа (касса/сайт).

**Что можно использовать повторно:** модель заказа и защита от дублей, снимки в `order_items`, станции кухни/бара и статусы, роли и RLS-подход, смены, `admin_report`, фоновые запросы и обработка ошибок в UI, система миграций с предусловиями и SQL-проверками.

## 3. Сайт

Статический демо-сайт (30 блюд, 9 категорий, 20 фото CC0, аллергены на уровне ингредиентов), корзина, оформление, имитация оплаты, страницы заказов, демо-админка. Всё в `localStorage`; сервера, защищённой авторизации и общей базы нет. GitHub Pages отдаёт только статику, поэтому настоящие заказы, роли и платежи без серверной части невозможны.

**Расхождения с настольной системой (их нужно устранить до интеграции):**

| Тема | Сайт (демо) | Приложение |

| Идентификатор блюда | slug (`cheeseburger`) | `menu_items.id` + числовой `code` |
| Данные блюда | описание, фото, состав, аллергены | только название, категория, цена, станция |

## 4. Предлагаемая единая архитектура

```
Сайт (GitHub Pages, статика) ──anon key──► Supabase (одна БД)
Касса/кухня/склад (Tkinter) ──staff JWT──►   ├─ публичные RPC (anon): public_menu(), web_place_order(), web_order_status(token)
Панель сайта / курьер (позже) ──staff JWT──► ├─ служебные RPC (staff, роль проверяется на сервере)
                                              └─ Edge Function (позже): вебхуки платежей, секреты
```

Принципы: одна таблица `orders` и один `place_order`-путь для кассы и сайта; сайт **никогда** не получает `service_role`; все публичные операции — узкие `SECURITY DEFINER` RPC с проверкой ввода на сервере; персональные данные клиента в отдельной таблице без прав для клиентов (только функции).

**Новые объекты (миграции начиная с 18; 17 зарезервирована за черновиком, его не трогаем):**
- Заказы: расширение `orders` (`source` ∈ pos/web, `fulfillment` ∈ dine_in/pickup/delivery, `payment_method`, `payment_status`), `order_customers` (имя, телефон, адрес — закрыта RLS), `order_tracking` (хеш токена, не сам токен), `web_place_order` — обёртка над общей логикой, с лимитом и идемпотентностью.
- Доставка: отдельная таблица `deliveries` со своими статусами (assigned/picked_up/en_route/delivered/failed), чтобы не менять `orders.status`, на который завязаны функции кухни и бара. Статус сайта «Передан курьеру» = `deliveries`, «Отменён» = `voided_at`.
- Меню для сайта: расширение `menu_items` (`slug`, описание, фото, текст состава, `allergens`) и `public_menu()` — только опубликованные поля.
- Склад: `stock_products` (единицы кг/г/л/мл/шт с базовой единицей), `suppliers`, `stock_receipts` и позиции (ключ идемпотентности), `recipes` и `recipe_items`, `stock_movements` (журнал только на добавление, остаток = сумма движений), `stock_counts` и позиции, `order_stock_deductions` (уникально по заказу — защита от двойного списания).
- Роли: расширить `profiles_role_check` (manager, stockkeeper, courier) — отдельная миграция и отдельное разрешение.
- Курьеры/GPS (этап 9): `courier_locations` с коротким сроком хранения; сейчас не создаётся.

**Момент списания (требует решения, мои предложения по умолчанию):** касса — при `place_order` (оплата на месте); сайт — при принятии заказа сотрудником (`accepted`), а не при создании, чтобы мусорные заказы не списывали склад; отмена до начала приготовления возвращает остатки, после начала — не возвращает без акта списания; возврат восстанавливает ровно один раз.

## 7. Риски и ориентиры по стоимости (ориентиры, не проверены по актуальным тарифам — перед выбором сверить)

- **Supabase:** бесплатный план подходит для разработки; для продакшена ориентир — платный тариф порядка десятков долларов в месяц (бэкапы, нет паузы проекта). Edge Functions и лимиты зависят от тарифа.
- **Карта:** тайлы `tile.openstreetmap.org` и публичный OSRM допустимы только для лёгкого демо; для коммерческого сайта нужен договорной поставщик тайлов/маршрутов (MapTiler, Stadia, Mapbox, Thunderforest — есть бесплатные квоты и ключи по домену) или собственный сервер.
- **Платежи (Казахстан):** провайдеры вроде Kaspi Pay, Halyk Epay, CloudPayments, Freedom Pay требуют юрлицо/ИП, договор, комиссия обычно порядка 1–3% — условия сверять отдельно.
- **Фискализация:** обычный чек ≠ фискальный; для Казахстана нужна онлайн-касса с передачей данных оператору фискальных данных — отдельный этап после согласования.
- **Фото 30 блюд профессионального уровня:** бесплатные CC0-снимки покрывают 20 блюд; единый студийный стиль для всех 30 — это либо стоковая подписка/лицензии, либо фотосъёмка, либо ИИ-генерация с обязательной пометкой. Решение за вами.
- **Термопринтер:** казахские буквы `қ ұ ү ғ ң і ә ө` не входят в стандартные кодовые страницы большинства ESC/POS-принтеров → вероятно придётся печатать текст растровым изображением; проверить можно только на реальном устройстве.
- **Безопасность:** анонимный RPC создания заказа — цель для спама; нужны лимиты, проверка ввода, капча/токен (вне чистого SQL), отслеживание только по неугадываемому токену.
